PART 4 — DO NOT DISCARD A VALID RESULT BECAUSE OF A TECHNICAL ATOMICITY-CHECK FAILURE
==================================================

Important distinction:

A. ATOMICITY CHECK SAYS CONTENT IS NON-ATOMIC
→ repair or reject according to canonical rules.

B. ATOMICITY CHECK ITSELF FAILS TECHNICALLY
for example timeout/parser/provider transport failure
→ this is NOT evidence that the mapping content is non-atomic.

Implement safe handling.

If atomicity verification cannot complete because of a transient technical failure:

- do not falsely mark the mapping as valid;
- do not falsely mark it non-atomic;
- preserve the generated candidate/result in temporary job state or retryable draft state if the existing architecture supports it;
- allow a bounded retry of ONLY the atomicity verification rather than regenerating the entire Mapping from scratch.

Use the smallest existing mechanism possible.

Do NOT create a new parallel Mapping storage model unless absolutely necessary.

The teacher should not lose all prior AI work merely because the atomicity verifier had a transient technical failure.
