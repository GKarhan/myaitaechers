==================================================
GOAL
==================================================

When a learner answers a quiz question and FINALIZES that answer,
the learner should receive immediate instructional feedback BEFORE
moving to the next question.

Minimum feedback:

1. Whether the learner was correct or incorrect.
2. The learner's submitted answer.
3. The correct answer.
4. A short instructional explanation of WHY that answer is correct.

For mathematical/calculation/problem questions, the feedback should
contain a concise solution/reasoning path when appropriate.

The learner should not merely memorize a result such as:

"Correct answer: 3250"

Instead, where appropriate, show something like:

Քո պատասխանը՝ 3000 գ
Ճիշտ պատասխանը՝ 3250 գ

Բացատրություն․
3 կգ = 3000 գ
3000 գ + 250 գ = 3250 գ

Then the learner explicitly continues to the next question.

==================================================
SECURITY / ANSWER-LEAK RULE
==================================================

This is mandatory.

The learner MUST NOT receive:

- correctOptionIndex
- correct answer
- answer key
- explanation revealing the answer
- worked solution

BEFORE the learner finalizes/submits that question.

If GET quiz currently exposes correctOptionIndex or equivalent to
the learner, report it as a correctness/security issue and fix it
within this task.

Teacher review may continue to receive the answer key.

Learner and teacher read models may therefore need to differ.

==================================================
CANONICAL INTERACTION
==================================================

For each question:

QUESTION
↓
learner selects/types answer
↓
learner clicks:

«Հաստատել պատասխանը»

↓
SERVER evaluates/persists the finalized answer
↓
SERVER returns authoritative immediate feedback
↓
UI locks that question's answer
↓
learner sees feedback
↓
learner clicks:

«Հաջորդ հարցը»

Only then move to the next question.

Do NOT determine correctness only in the browser.

The backend is authoritative.

==================================================
FEEDBACK UI
==================================================

After answer finalization, display a compact feedback block.

CORRECT example:

✅ Ճիշտ է

Քո պատասխանը՝ 3250 գ

Ճիշտ պատասխանը՝ 3250 գ

Բացատրություն
3 կգ = 3000 գ, հետևաբար
3 կգ 250 գ = 3250 գ։

[Հաջորդ հարցը]


INCORRECT example:

❌ Սխալ է

Քո պատասխանը՝ 3000 գ

Ճիշտ պատասխանը՝ 3250 գ

Բացատրություն
3 կգ = 3000 գ։
Դրան պետք է ավելացնել ևս 250 գ։
Ուստի՝ 3000 գ + 250 գ = 3250 գ։

[Հաջորդ հարցը]

Keep it concise and readable.

Do not create a new page.

==================================================
IMPORTANT — EXPLANATION MUST TEACH
==================================================

The explanation is not merely:

"Սա ճիշտ պատասխանն է։"

It should provide the minimum reasoning needed to understand why.

For factual/remember questions:

Question:
1 կգ-ը քանի՞ գրամ է։

Feedback may be:

1 կգ = 1000 գ, հետևաբար ճիշտ պատասխանն է 1000 գ։

For Understand questions:

Explain the relevant relationship/concept briefly.

For Apply questions:

Show the essential application/calculation steps.

For Analyze/Evaluate questions:

Show the key reasoning or distinction that justifies the correct answer.

Do NOT expose chain-of-thought style hidden reasoning.

We need a concise pedagogical explanation / solution, not internal model reasoning.

==================================================
EXPLANATION DATA CONTRACT
==================================================

First inspect whether an explanation/solution field already exists.

If a suitable persisted field already exists:
REUSE IT.

If generation already produces an explanation but it is discarded:
persist it through the smallest existing contract extension.

If no suitable field exists, add ONE canonical question-level field,
following existing naming conventions, for example:

answerExplanation

or

solutionExplanation

Do not add multiple overlapping fields.

This explanation belongs to the QUESTION / ANSWER KEY, not to a
student attempt.

It must be generated when the quiz question is created/reviewed,
not by making a new provider call every time a student answers.

CRITICAL:

Student answer submission must NOT trigger a provider/AI call merely
to explain the answer.

Immediate feedback must be fast and deterministic from persisted data.

==================================================
FINALIZED ANSWER RULE
==================================================

Once the learner clicks «Հաստատել պատասխանը»:

- persist/evaluate the answer
- lock the answer in the UI
- show feedback
- do not allow changing that finalized answer
- do not allow resubmitting the same question to discover the answer
  and then change it

Refresh must not reopen a finalized answer for editing.

If the existing attempt model cannot currently support this invariant,
report the exact gap before making a broad schema change.

Prefer reusing existing answer/attempt persistence.
