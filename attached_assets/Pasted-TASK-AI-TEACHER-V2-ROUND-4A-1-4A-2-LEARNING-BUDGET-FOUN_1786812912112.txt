PART 5 — ACTIVE LEARNING TIME — V1
============================================================

Implement the minimum safe server-owned active-time accounting model.

The design selected:

TURN-BASED CAPPED INTERVALS.

Concept:

On a qualifying learner interaction:

delta =
    now - lastActivityAt

credited =
    min(delta, ACTIVE_INTERVAL_CAP_SECONDS)

activeLearningSeconds += credited

lastActivityAt = now

But refine this carefully.

============================================================
PART 6 — ACTIVE INTERVAL CAP MUST BE POLICY, NOT MAGIC NUMBER
============================================================

The design proposed 180 seconds.

Do NOT scatter literal 180 values through runtime code.

Define one named policy constant, e.g.:

ACTIVE_INTERVAL_CAP_SECONDS

Initial V1 value may be 180 ONLY if consistent with the approved design.

The constant must be:
- centralized,
- documented,
- deterministic,
- easy to tune later.

This is a policy parameter, not learner state.

============================================================
PART 7 — DEFINE QUALIFYING ACTIVITY EXACTLY
============================================================

Do not count arbitrary HTTP requests as active learning.

For R4 V1, define and document which server-observed events qualify.

At minimum evaluate:

- learner ANSWER
- READY
- CONTINUE
- HELP
- CONFUSED
- REPEAT
- CLARIFY
- OFF_TOPIC
- session-state GET
- page refresh
- frontend polling

Required invariant:

GET requests, refresh hydration, polling, and passive page presence
must NOT accumulate active learning time.

Prefer counting meaningful learner-originated chat/task interactions.

Intent classification may affect pedagogy, but time accounting should
not accidentally count infrastructure traffic.

Document the final qualifying-event rule.

============================================================
PART 8 — FIRST ACTIVITY SEMANTICS
============================================================

Avoid this bug:

Session created at 10:00.
Learner does nothing.
First message at 10:30.
System credits 180 seconds of learning.

That is false.

Define safe first-activity semantics.

Preferred direction:

If lastActivityAt is NULL:
- establish activity anchor,
- credit 0 seconds for that first observed activity.

Then future qualifying interactions can credit capped intervals.

If repository evidence supports a better deterministic approach,
document it.

Do NOT credit idle time before the first learner activity.

============================================================
PART 9 — ACTIVE TIME UPDATE MUST BE SAFE
============================================================

The active-time increment and lastActivityAt update must be concurrency-safe.

Avoid a read-modify-write race where two requests can overwrite
activeLearningSeconds.

Use the repository's transaction/atomic update capabilities.

If PostgreSQL expression update is available, prefer an atomic increment.

Document exactly how concurrent requests are handled.

============================================================
PART 10 — SESSION BUDGET DERIVATION
============================================================

Backend must be able to deterministically derive:

sessionBudgetSeconds =
    requiredSessionMinutes * 60

remainingRequiredSeconds =
    max(0, sessionBudgetSeconds - activeLearningSeconds)

sessionBudgetExhausted =
    requiredSessionMinutes IS NOT NULL
    AND activeLearningSeconds >= sessionBudgetSeconds

Do NOT persist remainingRequiredSeconds unless absolutely necessary.

Prefer deriving it.

Do NOT persist sessionBudgetExhausted if it is safely derivable.

============================================================
PART 13 — SESSION TIME LIMIT ≠ FAILURE
============================================================

HARD INVARIANT.

TIME_BUDGET_EXHAUSTED must NEVER fabricate negative cognitive evidence.

Example:

Target:
remember → understand → apply

Learner demonstrated:
remember ✓
understand ✓

Required time expires before Apply is attempted.

Correct:

demonstratedCognitiveLevel = understand
apply = NOT YET EVALUATED / DEFERRED

Incorrect:

apply = failed

Therefore on pure time exhaustion:

- do not write incorrect-answer evidence,
- do not increment failed attempt count,
- do not lower demonstrated cognitive level,
- do not mark an unattempted cognitive level as failed,
- do not pretend remediation was exhausted.

Add structural tests proving this.

PART 14 — IMPORTANT REVISIT SEMANTICS
============================================================

Distinguish at least:

A. REMEDIATION_EXHAUSTED
Learner actually attempted the level and bounded remediation failed.

B. LOCAL_BUDGET_EXHAUSTED
Learner worked on the active MicroNode/level, but continuing now is
not justified within the local effort budget.

C. SESSION_TIME_LIMIT
Overall required session ended before unfinished curriculum could be
completed/evaluated.

These are not equivalent.

Rules for R4A.1 + R4A.2:

REMEDIATION_EXHAUSTED:
- revisitRequired = true
- revisitReason = REMEDIATION_EXHAUSTED

LOCAL_BUDGET_EXHAUSTED:
- revisitRequired = true
- revisitReason = LOCAL_BUDGET_EXHAUSTED

SESSION_TIME_LIMIT:
Do NOT automatically mark every unfinished/unvisited MicroNode as
revisitRequired.

For the currently active MicroNode, determine whether an explicit
defer marker is necessary.

Do NOT classify pure time expiry as cognitive failure.

If R4A.3 is the cleaner place to persist session-limit defer state,
defer that part and report it.
