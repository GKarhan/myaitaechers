FINAL MAPPING PIPELINE STABILIZATION
SELF-REPAIR + WARNING-FIRST + TRUE HARD-BLOCK ONLY

GOAL

This is the final stabilization task for the Teacher Mapping workflow before we begin multi-lesson quality validation.

The teacher must NOT have to debug C1/C2/internal readiness problems created by the automatic mapping pipeline.

The normal workflow must remain simple:

Lesson created
→ Goal/outcomes confirmed
→ Automatic mapping
→ Step 1: Generate Cognitive Paths
→ Step 2: Generate Teaching Content
→ Teacher reviews/edits
→ Step 3: Final lesson approval

IMPORTANT:
Do NOT redesign the mapping architecture.
Do NOT weaken C1–C7 authority/safety semantics.
Do NOT bypass source-grounding requirements.
Do NOT silently approve invalid content.
Do NOT touch AI Teacher runtime, Quiz, Knowledge Tree, student flow, or unrelated features.
Do NOT publish/deploy.

==================================================
PART 1 — CANONICAL POLICY
==================================================

Implement one consistent readiness policy for the mapping pipeline.

There must be THREE semantic outcomes:

GREEN — READY
The node is valid and the pipeline continues normally.

YELLOW — REVIEW REQUIRED
The system produced a usable, source-grounded result, but teacher review is recommended.

YELLOW MUST NOT stop the normal generation pipeline when safe continuation is possible.

The generated result must be preserved and clearly marked for teacher review.

RED — BLOCKED
Use RED only when safe generation cannot continue.

Examples of legitimate RED conditions:

- required source content is missing/unreadable;
- the MicroNode cannot be grounded in the source;
- required canonical data cannot be derived safely;
- source and objective materially contradict each other;
- continuing would require inventing unsupported curriculum content;
- canonical C1/C2 requirements cannot be satisfied even after bounded repair.

Do NOT convert real RED safety failures into warnings.

==================================================
PART 2 — BOUNDED AUTOMATIC REPAIR
==================================================

For internal AI-generated readiness problems, the system should attempt bounded automatic repair BEFORE asking the teacher to intervene.

Examples:

- C1 generated but marked needs_review for a repairable grounding/alignment reason;
- generated objective slightly exceeds supported source scope;
- target ceiling does not match canonical C1 constraints;
- C2 candidate violates C1 ceiling;
- stale/inconsistent generated readiness state;
- generated Teaching Content candidate fails a repairable validation rule.

Use existing canonical generators/validators where possible.

Do NOT create parallel C1/C2 logic.

Maximum automatic repair must be bounded.

Suggested contract:

initial generation
→ canonical validation
→ if repairable: ONE targeted repair/regeneration
→ canonical validation again
→ READY / REVIEW_REQUIRED / BLOCKED

Do NOT create infinite retries.

Do NOT relax validators simply to make generation pass.

==================================================
PART 3 — C1 BEHAVIOR
==================================================

C1 must stop being a routine teacher-facing technical obstacle.

If C1 is source-grounded and usable but has a non-critical review concern:

DO NOT hard-block the whole Teaching Content workflow.

Persist it as REVIEW_REQUIRED and allow safe downstream processing.

If the C1 issue is automatically repairable:
repair it once and revalidate.

Only RED C1 failures should stop downstream generation.

The teacher should not need to understand internal C1 mechanics during normal operation.

Do NOT remove C1.
Do NOT weaken C1 grounding.
Do NOT fake C1 readiness.

==================================================
PART 4 — C2 / COGNITIVE PATH BEHAVIOR
==================================================

Preserve all previously established C2 safety rules:

- C2 must respect C1 target ceiling.
- C2 must never invent a higher unsupported cognitive ceiling.
- C2 must remain source/C1 grounded.
- existing valid/teacher-edited paths must not be overwritten automatically.

For an AI-generated invalid C2 candidate:

perform at most ONE constrained repair/regeneration using the canonical C1 ceiling.

If the repaired result passes:
persist it.

If usable but requiring non-critical review:
mark REVIEW_REQUIRED and continue where safe.

If canonical validity still cannot be achieved:
RED/BLOCKED.

Do NOT force acceptance.

==================================================
PART 5 — TEACHING CONTENT BULK GENERATION
==================================================

The lesson-wide Teaching Content action should behave like a robust orchestration layer.

For every MicroNode:

1. inspect canonical readiness;
2. auto-repair eligible internal C1/C2 problems;
3. generate Teaching Content for all nodes that are safely usable;
4. preserve review-required results;
5. block only nodes that remain genuinely unsafe.

ONE problematic node must NOT destroy valid results generated for other nodes.

Never delete already valid Teaching Content because another node failed.

The final result should summarize:

READY: X
REVIEW REQUIRED: Y
BLOCKED: Z

Do not expose internal technical noise unless the teacher opens details.

PART 8 — FINAL APPROVAL
==================================================

Final lesson approval remains the authoritative teacher gate.

It may proceed only when there are ZERO RED/BLOCKED conditions.

YELLOW / REVIEW_REQUIRED content must NOT be silently treated as teacher-approved.

If review-required items remain, the final approval UI must clearly tell the teacher what needs review.

The teacher can inspect/edit those items and then explicitly perform the single final lesson approval.

Do not introduce separate approval buttons for every generated object.

Avoid repeated “✅ Հաստատված” UI noise on every exercise/node if it is not required for an actual teacher action.

Preserve underlying status semantics even if the repetitive visual badge is removed.
