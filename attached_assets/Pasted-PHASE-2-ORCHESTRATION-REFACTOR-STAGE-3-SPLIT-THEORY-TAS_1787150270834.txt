PHASE 2 ORCHESTRATION REFACTOR — STAGE 3
SPLIT THEORY / TASK / FEEDBACK AI CONTRACTS
SERVER ACTION → BOUNDED AI JOB

Stage 0 regression baseline is frozen and green.
Stage 1 orchestration seam is complete.
Stage 2 server-owned action planning is complete.

Stage 2 established the core authority rule:

AUTHORITATIVE SERVER STATE
→ SERVER ACTION PLAN
→ AI CONTENT
→ SERVER VALIDATION
→ TASK / EVALUATION AUTHORITY
→ DECISION ENGINE
→ PERSISTENCE

Stage 3 now removes the next major architectural coupling:

A single general structured AI response must no longer simultaneously own
THEORY content, task creation, answer evaluation metadata, feedback wording,
and workflow-shaped fields for all Phase-2 jobs.

==================================================
GOAL
==================================================

Split Phase-2 AI work into bounded job contracts:

1. THEORY JOB
   Explain the current MicroNode / cognitive target.

2. TASK JOB
   Produce a MICRO_CHECK candidate only when the backend has already decided
   that a generated MICRO_CHECK is required.

3. FEEDBACK JOB
   Produce learner-facing feedback only after authoritative correctness and
   pedagogical action are already known.

The backend remains authoritative for workflow.

Target architecture:

STUDENT MESSAGE
      ↓
chat.ts
      ↓
LOAD AUTHORITATIVE STATE
      ↓
SERVER ACTION PLANNER
      ↓
┌─────────────────────────────┐
│ DELIVER_THEORY              │
│ → THEORY AI CONTRACT        │
└─────────────────────────────┘
      ↓
SERVER VALIDATION
      ↓
THEORY RESPONSE
      ↓
STOP / WAIT FOR NEXT ACTION

Then:

SERVER ACTION PLANNER
      ↓
NEXT TASK REQUIRED
      ↓
SOURCE EXERCISE AVAILABLE?
      │
      ├── YES
      │    → backend selects eligible exact source exercise
      │    → activate exact activeLessonExerciseId
      │    → backend renders authoritative source text
      │
      └── NO
           → TASK AI CONTRACT
           → validate candidate
           → activate exact generated MICRO_CHECK payload
      ↓
STUDENT ANSWERS
      ↓
AUTHORITATIVE EVALUATION
      ↓
PEDAGOGICAL DECISION ENGINE
      ↓
FEEDBACK AI CONTRACT
      ↓
SERVER APPLIES PROGRESSION / REMEDIATION
      ↓
RESPONSE

==================================================

==================================================
PART 2 — THEORY CONTRACT
==================================================

THEORY AI must NOT decide workflow.

Input should contain only the authoritative educational/context data needed to
explain the current target, such as existing approved fields where applicable:

- current MicroNode
- current cognitive level
- learning objective
- approved/student-facing explanation
- theory content
- verbatim grounding anchor
- examples
- misconception/non-example data
- learner/session adaptation context already legitimately used

Do not invent new curriculum data.

Output should be minimal.

Conceptually:

{
  student_message: string,
  source_fidelity: ...
}

Only include additional fields if genuinely required for current safety
validation.

THEORY output must NOT contain authoritative:

- teaching_mode
- is_micro_check
- node_decision
- answer_evaluation
- interaction_type
- options
- correct_option
- progression decision
- completion decision

THEORY is explanation only.

==================================================
PART 3 — THEORY TURN MUST NOT CREATE TASK
==================================================

Required invariant:

DELIVER_THEORY
→ explanation only
→ no active task created
→ no answer key created
→ no evidence created
→ no progression
→ no MICRO_CHECK state activation

A THEORY provider failure must leave:

- same node
- same cognitive level
- THEORY
- no active task
- no phantom evidence/progression

Do not require THEORY output to also contain a MICRO_CHECK.

This intentionally removes the old fragile contract:

TEACH
+ is_micro_check=true
+ explanation
+ question
+ task metadata

from the THEORY job.

==================================================
PART 4 — SERVER-OWNED NEXT LEARNING ACTION
==================================================

After THEORY has been successfully delivered, the backend must own what comes
next.

Audit current stage/session semantics before implementing this.

The backend must not depend on the THEORY AI response to decide whether a task
exists.

Establish the minimum explicit server state/transition required to represent:

THEORY DELIVERED
→ NEXT CHECK/TASK REQUIRED

Prefer existing stage/state fields if they can represent this safely.

Do NOT add a DB migration unless absolutely required.

If current nodeTeachingStage semantics can safely represent the transition,
reuse them.

If they cannot, STOP and report the exact blocker before inventing schema.

==================================================
PART 5 — SOURCE EXERCISE FIRST
==================================================

When the server has decided a task/check is required:

Inspect eligible current-node/current-level source exercises using the existing
authoritative exercise eligibility logic.

If an eligible source exercise is available:

BACKEND selects the exact exercise.

AI must NOT select:

source_fidelity.exercise_id

as the authoritative identity.

Required authority:

eligible exercise set
→ backend deterministic selection policy
→ exact lesson_exercises row
→ persist activeLessonExerciseId
→ backend-owned verbatim delivery

Preserve existing exact-source and single-delivery safeguards.

Do NOT reintroduce classExercises[0] as an independent authority.

If current code has an existing deterministic ordering/sequence rule, use it.

Do not invent a new pedagogical exercise-ranking algorithm in this task.

==================================================
PART 6 — GENERATED MICRO_CHECK ONLY WHEN NEEDED
==================================================

Only if the server has decided a check is required AND no eligible source
exercise is selected for that check should the TASK AI job run.

The TASK AI job does one thing:

GENERATE ONE MICRO_CHECK CANDIDATE.

It does not teach theory.
It does not evaluate an answer.
It does not provide feedback.
It does not decide progression.

==================================================
PART 7 — TASK CONTRACT
==================================================

Define a bounded generated-task result.

Support only interaction types already supported by current architecture.

For example:

multiple_choice
true_false
constructed_response

Use current canonical naming.

Conceptually:

{
  student_message: string,
  interaction_type: ...,
  options: ...,
  correct_option: ...,
  question_template: ...,
  source_fidelity: ...
}

But include only fields actually required by current task activation and safety
logic.

Objective tasks:

multiple_choice:
- structured options required
- canonical correct option required
- visible rendered options must match structured options

true_false:
- canonical TRUE/FALSE correct answer required
- visible answer choices must be renderable/validated deterministically

constructed_response:
- no deterministic answer key
- explicit visible answerable question/task required

TASK result must NOT contain:

- answer_evaluation
- node_decision
- teaching_mode authority
- progression decision
- completion decision

NO VALID TASK
→ NO ACTIVE TASK.

PART 10 — ANSWER TURN
==================================================

When the learner answers an active task:

Do NOT ask the general AI response to decide correctness first and then repair
it afterward where deterministic authority exists.

Use existing authoritative evaluation before FEEDBACK generation.

Generated objective MICRO_CHECK:
activeObjectiveTaskPayload
→ deterministic correctness

Typed source exercise:
activeLessonExerciseId
→ exact row
→ deterministic correctness

Constructed response / legacy unsupported task:
preserve current AI-assisted evaluation behavior for now.

Do not invent semantic deterministic scoring for open responses.

==================================================
PART 11 — FEEDBACK CONTRACT
==================================================

After correctness is known and the Decision Engine has produced its
authoritative pedagogical result, call the bounded FEEDBACK AI job.

The feedback AI receives facts, not authority.

Input should include only what is needed, for example:

- task/question
- learner answer
- authoritative correctness
- correct/incorrect evidence where available
- current concept
- error/remediation context
- Decision Engine pedagogical action
- allowed feedback strategy
- source fidelity context where needed

Output should primarily be:

{
  student_message: string
}

Include minimal additional metadata only if genuinely needed for existing
feedback safety validation.

FEEDBACK AI must NOT decide:

- CORRECT / INCORRECT when backend authority exists
- evidence quality when backend authority exists
- cognitive-level advance
- MicroNode completion
- next stage
- next active task
- source exercise identity

==================================================
PART 12 — FEEDBACK MUST NOT APPEND NEXT TASK
==================================================

Required invariant:

FEEDBACK
→ feedback only
→ no next MICRO_CHECK appended
→ no source exercise appended
→ no task activation hidden behind feedback

The next learning action must be a server-owned subsequent action.

This preserves the already-established rule that feedback cannot manufacture
an active MICRO_CHECK.

==================================================
PART 13 — DECISION ENGINE ORDER
==================================================

→ server progression/remediation action
→ FEEDBACK generation using known result/action
→ persistence according to existing safe ordering

Audit existing evidence-write timing carefully.

Do NOT accidentally make feedback generation authoritative for progression.

Do NOT duplicate evidence writes.

Do NOT change thresholds.

PART 18 — RETRY / FAILURE SEMANTICS
==================================================

Each bounded job should have job-specific validation failure behavior.

THEORY failure:
→ remain safely ready to deliver THEORY
→ no task/evidence/progression mutation

TASK failure:
→ no active task
→ do not expose invalid task
→ remain in safe pre-task state

FEEDBACK failure:
→ do not reverse authoritative correctness/progression
→ preserve consistent session state
→ return the safest existing controlled failure behavior

Do not silently fall back to the old general AI contract for NEW normal
Stage-3 jobs merely because a bounded job failed.

That would recreate the old architecture.
