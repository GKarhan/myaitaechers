PHASE 1.5 — Granularity + Learning Objective Validation

==================================================
1. GOAL
==================================================

The Mapper already creates MicroNodes with `learningObjective`.

However, audit/review has shown that some MicroNodes may be:

- missing a Learning Objective
- suspiciously broad / mega-nodes
- multi-objective nodes

For V1 we are NOT building a new AI validation system.

We are adding deterministic validation + Teacher Review warnings.

Required semantics:

1. Missing/blank Learning Objective → BLOCKING ERROR
2. Suspicious mega-node → WARNING
3. Suspicious multi-objective Learning Objective → WARNING

The teacher may edit/split the MicroNode after seeing a warning.

Warnings DO NOT automatically block approval.

Missing Learning Objective DOES block approval.

Most important invariant:

NO APPROVED MICRONODE MAY EXIST WITHOUT A NON-EMPTY LEARNING OBJECTIVE.

3. LEARNING OBJECTIVE — BLOCKING VALIDATION
==================================================

Implement a backend-authoritative invariant:

A MicroNode cannot become `approved` if:

- learningObjective is null
- learningObjective is undefined
- learningObjective is empty
- learningObjective contains whitespace only

Normalize with `.trim()` for validation.

Example:

learningObjective = ""

→ BLOCK

learningObjective = "    "

→ BLOCK

learningObjective = null

→ BLOCK

learningObjective =
"Աշակերտը կարող է սահմանել բնությունը։"

→ valid

IMPORTANT:

Do NOT rely only on frontend validation.

The backend approval path MUST enforce this invariant.

If the existing node update endpoint can change `learningObjective` after approval, prevent this sequence:

1. approved node has valid LO
2. teacher edits LO to blank
3. node remains approved

Choose the smallest architecture-consistent solution.

Acceptable behavior:

- reject clearing LO while node is approved

OR

- automatically move the node back to draft/review state

Prefer the behavior most consistent with the current repository's approval semantics.

Do not invent a new workflow state unless required.

==================================================
5. GRANULARITY WARNING — V1
==================================================

We do NOT want an AI call.

Implement a small deterministic heuristic that identifies only clearly suspicious cases.

The purpose is NOT to mathematically determine whether a node is pedagogically perfect.

The purpose is to warn the teacher that manual review may be useful.

A suspicious mega-node may be detected from existing fields such as:

- unusually long Learning Objective
- unusually long theory/content relative to other MicroNodes
- obvious multiple-objective linguistic structure
- other simple deterministic signals already supported by the current data model

IMPORTANT:

Avoid aggressive false positives.

A long theory section alone should NOT automatically mean the node is invalid.

Granularity findings are WARNING only.

They must NOT automatically:

- split a MicroNode
- rewrite content
- change LO
- call AI
- modify Mapper output
- block approval

==================================================
6. MULTI-OBJECTIVE WARNING
==================================================

Add a conservative deterministic heuristic for suspicious multi-objective LOs.

Example suspicious pattern:

`Աշակերտը կարող է սահմանել X, բացատրել Y և համեմատել Z։`

This may represent several distinct learning objectives.

But:

`Աշակերտը կարող է բացատրել X և բերել օրինակներ։`

should NOT automatically be considered invalid merely because the word
`և`
exists.

Therefore DO NOT implement:

`if learningObjective.includes("և") → warning`

Use a conservative rule based on multiple distinct action verbs / objective structures.

Reuse Bloom/action-verb knowledge already present in the repository if such a deterministic list exists.

Do not add an AI call.

==================================================
7. WARNING SEMANTICS
==================================================

Warnings are informational.

Examples:

`🟠 Զգուշացում․ ուսուցման նպատակը կարող է ներառել մեկից ավելի ուսումնական նպատակ`

`🟠 Զգուշացում․ հանգույցը կարող է չափազանց լայն լինել`

The teacher may:

- edit the MicroNode
- split it manually using the existing CRUD
- ignore the warning and keep the MicroNode

WARNING must NOT prevent node approval.

ERROR must prevent node approval.
