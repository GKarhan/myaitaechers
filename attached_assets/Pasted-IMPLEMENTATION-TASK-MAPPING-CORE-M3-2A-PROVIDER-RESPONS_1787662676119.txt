==================================================

==================================================

For Lesson 717 job 190:

==================================================
1. SEPARATE THE FAILURE STAGES
==================================================

Refactor the existing M3-2 provider boundary minimally so these stages are
distinguishable:

A. REQUEST_FAILED
Provider/client call throws before a usable response is received.

B. EMPTY_RESPONSE
Provider call succeeds but no usable response content exists.

C. INVALID_JSON
Response content exists but JSON parsing fails.

D. SCHEMA_INVALID
JSON parsing succeeds but the parsed M3-2 response fails contract/schema
validation.

E. SUCCESS
Response is received, parsed, and validated successfully.

Use the project's existing naming/style conventions where appropriate.

Do NOT change the semantic schema itself.

==================================================
2. RESPONSE RECEIVED MUST BE FACTUALLY CORRECT
==================================================

Once model response content has been received:

responseReceived = true

must remain true even if:

- JSON parsing fails, or
- schema validation fails.

A local parser/validator failure must never be recorded as if the provider
returned no response.

==================================================
3. RETRY BEHAVIOR
==================================================

Preserve the existing bounded retry count:

attempt 1
→ one retry
→ stop

Do not add additional provider calls.

INVALID_JSON and SCHEMA_INVALID may use the existing single retry path.

Do not change candidate-level semantics or promotion behavior.

==================================================
4. SAFE PER-ATTEMPT DIAGNOSTICS
==================================================

Persist/retain only safe metadata necessary to diagnose M3-2 failures.

For each attempt, where available:

- attempt number
- model
- startedAt
- endedAt
- durationMs
- responseReceived
- responseContentLength
- finishReason
- HTTP status
- safe provider error code
- exception class
- sanitized exception message
- parseState
- validationState
- failure classification

Do NOT persist:

- raw model response
- source text
- exercise text
- prompt contents
- credentials
- API keys
- authorization headers

If a value is unavailable, leave it null/absent rather than inventing it.

==================================================
5. PRESERVE THE EXISTING SAFETY GATE
==================================================

The Task #191 pre-persistence protection must continue to work.

If M3-2 cannot produce valid semantic decisions after its allowed attempts:

- promotion remains fail-closed
- destructive canonical replacement must not begin
- previous canonical mapping must remain preserved

Do NOT weaken this gate.

The gate may consume the improved technical classification, but its safety
behavior must remain equivalent or stricter.
