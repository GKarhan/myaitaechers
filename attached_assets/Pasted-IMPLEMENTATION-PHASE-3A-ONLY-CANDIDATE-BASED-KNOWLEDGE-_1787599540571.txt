1. FUNDAMENTAL DOMAIN RULE
════════════════════════════════════════════════════════════

A source block is NOT automatically a MicroNode.

A paragraph, note, worked example, exercise, heading, visual, explanation,
definition, formula, table, instruction, or textbook fragment is SOURCE
MATERIAL.

A MicroNode is a pedagogical knowledge unit.

These are different concepts.

The mapper must first understand source material and form knowledge candidates.

Only candidates that satisfy the MicroNode promotion contract may become
MicroNodes.

Canonical architecture:

Verified Pass 1 Source Blocks
        ↓
Durable Source Material
        ↓
Knowledge Candidates
        ↓
Promotion Decision
        ↓
┌───────────────────────────────┐
│ PROMOTE_TO_MICRONODE          │
│ SUPPORT_EXISTING_MICRONODE    │
│ EXERCISE                      │
│ ACTIVITY_OR_HOMEWORK          │
│ STRUCTURAL_MATERIAL           │
│ UNRESOLVED_REVIEW             │
│ EXCLUDED_WITH_REASON          │
└───────────────────────────────┘
        ↓
Only PROMOTE_TO_MICRONODE
creates a MicroNode.

Everything else remains preserved in lesson_source_materials.

NO verified source material may disappear merely because it was not promoted.

════════════════════════════════════════════════════════════
2. WHAT COUNTS AS A MICRONODE
════════════════════════════════════════════════════════════

A MicroNode must represent ONE atomic learnable knowledge unit.

It must satisfy ALL required conditions:

1. LEARNABLE

There is something meaningful the learner can know, understand, or do.

2. INDEPENDENTLY ASSESSABLE

We can reasonably ask:

“Has the learner learned this specific thing?”

3. ATOMIC

It represents one pedagogical objective rather than several independent
objectives bundled together.

4. SOURCE-GROUNDED

The candidate has sufficient verified source evidence.

5. PEDAGOGICALLY NECESSARY

It deserves learner-state tracking independently.

If removing it as a separate MicroNode would lose an important independently
trackable learning target, it probably deserves promotion.

If it merely helps explain another learning target, it probably does NOT.

════════════════════════════════════════════════════════════
3. WHAT MUST NOT BECOME A MICRONODE BY DEFAULT
════════════════════════════════════════════════════════════

Do NOT create independent MicroNodes merely because the textbook contains:

- a heading
- section title
- transition sentence
- repeated explanation
- repeated rule
- repeated example
- worked-example narration
- exercise instruction
- answer key
- page metadata
- decorative text
- contextual introduction
- supporting NOTE
- supporting REMARK
- table caption
- figure caption
- isolated visual fragment
- malformed OCR fragment
- incomplete formula fragment
- motivational text
- recap wording that contains no independent learning target

These must remain source material and may support a promoted MicroNode.

IMPORTANT:

Do NOT implement this as a simplistic blockType blacklist.

A NOTE, EXAMPLE, TABLE, or similar block CAN contain an independent
instructional concept.

Classification must be semantic and evidence-based.

════════════════════════════════════════════════════════════
5. PROMOTION MUST BE EXPLICIT
════════════════════════════════════════════════════════════

Every KnowledgeCandidate must receive an explicit promotion decision.

There must be NO implicit:

candidate exists → therefore create MicroNode

behavior.

Use the existing Phase 1 pure promotion logic as the foundation.

A candidate may become a MicroNode only if promotion explicitly allows it.

At minimum, promotion must evaluate:

- semantic instructional value
- independent assessability
- atomicity
- source support
- duplication / semantic overlap
- uncertainty
- whether the content is merely supporting another candidate

Promotion decisions must carry machine-readable reasons.

Do not rely only on free-form explanation text.

════════════════════════════════════════════════════════════
6. SUPPORTING MATERIAL MUST ATTACH, NOT COMPETE
════════════════════════════════════════════════════════════

When material explains, illustrates, qualifies, demonstrates, or supports an
already promoted knowledge unit, prefer:

SUPPORT_EXISTING_MICRONODE

rather than creating another MicroNode.

Examples:

Rule:
“The sign of a product depends on the number of negative factors.”

This may be a core knowledge candidate.

Worked examples demonstrating the rule should normally support that knowledge
unit rather than becoming separate MicroNodes.

A note clarifying a special case should normally support the relevant
MicroNode unless the note itself introduces independently assessable knowledge.

Preserve the supporting material in lesson_source_materials and retain its
relationship/provenance where the current architecture supports it.

Do not duplicate source ownership merely to express support.

Respect the source-ownership invariant already enforced by coverage validation.

════════════════════════════════════════════════════════════
7. EXERCISES ARE EVIDENCE/TASKS, NOT KNOWLEDGE NODES
════════════════════════════════════════════════════════════

Exercises, activities, questions, and homework must not become MicroNodes
merely because they contain instructional language.

They remain exercise/activity entities and may be linked to the MicroNode(s)
they assess or practice.

Preserve the existing exercise persistence behavior unless a narrowly required
change is necessary for candidate promotion.

Do not redesign quiz generation or cognitive paths in this phase.

════════════════════════════════════════════════════════════
8. DUPLICATE HANDLING — IMPORTANT ARCHITECTURAL CHANGE
════════════════════════════════════════════════════════════

The current mapper has historically suffered from duplicate/near-duplicate
MicroNodes because semantic duplicate review happens after nodes are already
formed.

Move the conceptual duplicate decision earlier:

KnowledgeCandidate
→ compare semantic learning target
→ promotion / support / review
→ THEN MicroNode creation.

Candidate similarity is a SIGNAL, not proof.

Do NOT merge two candidates merely because token/Jaccard similarity crosses a
threshold.

The semantic question is:

“Would these candidates require separate learner mastery states?”

If NO:
they should normally resolve into one promoted MicroNode with combined source
support.

If YES:
they remain distinct even if wording is similar.

Examples:

“Determine the sign of a product”
and
“Explain why the sign of a product depends on the number of negative factors”

may represent different cognitive expectations but could still belong to the
same underlying knowledge unit with a cognitive path.

Do NOT automatically create two MicroNodes merely because verbs differ.

This is especially important because Cognitive Path will later represent
Remember → Understand → Apply → etc.

MicroNode granularity must represent KNOWLEDGE UNIT granularity,
not Bloom-level granularity.

════════════════════════════════════════════════════════════
9. MICRONODE ≠ BLOOM LEVEL
════════════════════════════════════════════════════════════

This rule is mandatory.

Do NOT create separate MicroNodes such as:

- remember the rule
- understand the rule
- apply the rule

when all three refer to the SAME underlying knowledge unit.

That should normally be ONE MicroNode:

“Sign of a product”

and later its Cognitive Path can contain:

Remember
→ Understand
→ Apply
→ Analyze ...

MicroNode answers:

WHAT knowledge/skill is being learned?

Cognitive Path answers:

TO WHAT cognitive depth has the learner mastered it?

Do not mix these dimensions.

11. UNCERTAINTY — FAIL SAFE WITHOUT DESTROYING THE MAP
════════════════════════════════════════════════════════════

If candidate promotion is uncertain:

DO NOT invent confidence.
DO NOT silently promote.
DO NOT discard the source.

Use the existing review-required architecture.

The structurally safe map should still be persistable as a teacher-reviewable
draft when appropriate.

Uncertain source material remains durable.

If a candidate is sufficiently formed to be useful but promotion requires
teacher judgment, preserve the appropriate review metadata/status using the
existing review architecture.

Do NOT weaken any hard source-integrity gate.

Hard failures remain hard failures:

- parser/contract corruption
- invalid source references
- impossible block IDs
- unsafe source coverage
- broken transaction integrity
- invalid activity ownership
- any condition that would lose or corrupt source material

Pedagogical uncertainty is NOT the same as structural corruption.

12. SOURCE FIDELITY
════════════════════════════════════════════════════════════

Never fabricate textbook content.

Every promoted MicroNode must remain traceable to verified source material.

Every supporting item must remain traceable to verified source material.

Every excluded/unresolved item must remain preserved in durable source
materials with its reason/disposition.

Teacher edits to a MicroNode must not overwrite or destroy canonical source
material.

Maintain the Phase 2 source-material independence invariant.

════════════════════════════════════════════════════════════
13. DO NOT DELETE USEFUL INFORMATION
════════════════════════════════════════════════════════════

Candidate consolidation must combine provenance, not throw it away.

If Candidate A and Candidate B resolve to the same underlying knowledge unit:

- create/retain one promoted MicroNode
- preserve all relevant source evidence
- preserve supporting material
- preserve machine-readable consolidation/review reasons where appropriate
- preserve exercises independently

Do NOT simply delete the “losing” candidate's source blocks.

Remember:

candidate deletion ≠ source deletion.

Source material always survives in lesson_source_materials.

15. COST AND PERFORMANCE
════════════════════════════════════════════════════════════

Do NOT add an AI call per candidate.

That architecture would be slow and expensive.

Prefer:

1. one structured generation producing candidate information
2. deterministic local promotion where confidence is sufficient
3. one bounded semantic review batch only for genuinely ambiguous candidates

Reuse existing duplicate/atomicity review calls where possible rather than
stacking new calls.

Target:

O(1) or small bounded number of AI calls per lesson stage,
NOT O(number of candidates).

Deterministic logic should handle obvious cases.

AI semantic review should handle ambiguity.
