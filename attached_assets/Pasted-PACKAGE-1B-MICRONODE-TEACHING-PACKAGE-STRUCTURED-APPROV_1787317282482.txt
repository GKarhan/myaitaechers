PACKAGE 1B — MICRONODE TEACHING PACKAGE
STRUCTURED, APPROVED, REUSABLE TEACHING CONTENT

IMPLEMENTATION TASK — ADDITIVE EXTENSION

CONTEXT

Package 1A is complete.

The system now has the C1 curriculum foundation for:

Lesson
→ canonical Lesson Outcomes
→ Outcome↔MicroNode alignment
→ REQUIRED/SUPPORTING
→ required cognitive depth
→ existing MicroNode Cognitive Path

Do NOT redesign or undo Package 1A.

This package implements the next C1 layer:

MicroNode

The Teaching Package exists so that future AI Teacher runtime behavior
can rely primarily on pre-generated / teacher-reviewed / approved

════════════════════════════════════════════════════
0 — GOAL
════════════════════════════════════════════════════

For every MicroNode, provide a structured, persistent, teacher-reviewable
Teaching Package.

The package must be capable of storing reusable pedagogical content such
as:

1. MAIN_EXPLANATION
2. KEY_FACT
3. RULE_OR_FORMULA
4. EXAMPLE
5. COUNTEREXAMPLE
6. MISCONCEPTION
7. ALTERNATIVE_EXPLANATION
8. GUIDING_QUESTION
9. HINT
10. RESOURCE

Do NOT store the entire Teaching Package as one large undifferentiated
text blob.

Teaching Package items must be independently manageable and reusable.

The architecture must support future AI Teacher logic such as:

MicroNode MN7
+ Cognitive Level UNDERSTAND
→ use approved explanation A
→ use example B
→ if misconception X appears, use contrast/counterexample C
→ if learner needs help, use hint H1
→ then select an eligible task

But DO NOT implement that runtime selection logic in this task.

════════════════════════════════════════════════════
4 — ITEM TYPES
════════════════════════════════════════════════════

Support these canonical pedagogical item types:

MAIN_EXPLANATION

Purpose:
The primary approved explanation of the MicroNode.

KEY_FACT

Purpose:
Important fact/definition/property the learner should retain.

RULE_OR_FORMULA

Purpose:
Rule, formula, algorithmic principle, grammatical rule, etc.

EXAMPLE

Purpose:
Positive worked/conceptual example.

COUNTEREXAMPLE

Purpose:
Contrast/non-example/counterexample useful for concept boundaries and
misconception correction.

MISCONCEPTION

Purpose:
A known likely learner misconception or error pattern.

ALTERNATIVE_EXPLANATION

Purpose:
A second explanation strategy if the main explanation does not work.

GUIDING_QUESTION

Purpose:
A question used to guide learner reasoning without directly giving the
answer.

HINT

Purpose:
Progressive assistance/scaffolding.

RESOURCE

Purpose:
Supporting resource/material/reference.

Do NOT add dozens of types in this package.

If current repository evidence shows one additional type is essential,
document why before adding it.

════════════════════════════════════════════════════
5 — MAIN EXPLANATION RULE
════════════════════════════════════════════════════

A MicroNode should be able to have one PRIMARY approved
MAIN_EXPLANATION.

It may also have alternative explanations.

Do not represent every explanation as MAIN_EXPLANATION.

If multiple MAIN_EXPLANATION drafts exist during review, the system must
still be able to identify which approved one is primary.

Use the simplest implementation compatible with current schema
conventions.

Do not automatically replace an approved explanation when a new draft is
created.

════════════════════════════════════════════════════
6 — COGNITIVE LEVEL APPLICABILITY
════════════════════════════════════════════════════

Teaching Package items are MicroNode-owned.

However, some items may be especially appropriate for a particular
Cognitive Level.

Examples:

MAIN_EXPLANATION
→ may apply generally to the MicroNode

EXAMPLE
→ may be useful for UNDERSTAND

GUIDING_QUESTION
→ may target APPLY

HINT
→ may support APPLY

RESOURCE
→ may support ANALYZE

Therefore support:

MicroNode-wide item
OR
item applicable to a specific cognitive level.

Do NOT duplicate the entire Teaching Package per Cognitive Level.

Do NOT make Cognitive Level mandatory for every item.

If referencing current Cognitive Path rows directly would be fragile
because those rows can be regenerated/deleted, use a stable cognitive
level semantic identifier consistent with Package 1A's approach.

Inspect lifecycle before deciding.

════════════════════════════════════════════════════
7 — PROVENANCE
════════════════════════════════════════════════════

Every Teaching Package item must have traceable provenance.

Support at minimum the conceptual distinction:

SOURCE_MATERIAL
TEACHER_CREATED
AI_GENERATED
AI_GENERATED_TEACHER_APPROVED

If current project already has compatible provenance vocabulary, reuse or
map cleanly rather than creating competing semantics.

IMPORTANT:

AI-generated content is NOT automatically equivalent to approved
content.

Teacher approval must be explicit.

Future runtime generation will be a separate category/process and is NOT
implemented here.

Do not label existing source textbook content as AI-generated.

════════════════════════════════════════════════════

════════════════════════════════════════════════════

Teaching Package items must support review state.

Use current project status conventions where possible.

Conceptually we need at least:

DRAFT
APPROVED

already support it.

Future AI Teacher must eventually prefer APPROVED content.

But do NOT change AI Teacher in this task.

Teacher must be able to:

- review item
- edit item
- approve item
- return/edit draft
- delete where safe

Do not silently approve generated material.

════════════════════════════════════════════════════
9 — SOURCE CONTENT VS TEACHING CONTENT
════════════════════════════════════════════════════

Do NOT confuse:

SOURCE CONTENT

with

TEACHING CONTENT.

Source content preserves fidelity to the textbook/source.

Teaching Package represents pedagogically usable material derived from or
added around that source.

Do not move sourceContent/sourceQuote/sourceBlock data into Teaching
Package and then remove the source representation.

The source remains authoritative for source fidelity.

Teaching Package may reference or derive from it.

Where technically reasonable, preserve source reference/provenance.

════════════════════════════════════════════════════
11 — MISCONCEPTION MODEL
════════════════════════════════════════════════════

MISCONCEPTION is not merely another explanation.

It represents:

- likely incorrect understanding
- common error
- conceptual confusion
- incorrect rule/association

Keep it structured as its own item type.

For this package, content text is sufficient.

Do NOT build automatic misconception detection yet.

Do NOT modify AI Teacher error taxonomy yet.

Future AI Teacher will be able to match observed learner errors against
approved misconceptions.

════════════════════════════════════════════════════
12 — HINT MODEL
════════════════════════════════════════════════════

Multiple HINT items may exist for a MicroNode / Cognitive Level.

They must support ordering.

Example:

Hint 1
→ light cue

Hint 2
→ stronger scaffold

Hint 3
→ guided support

Do not require the current runtime AI Teacher to use them yet.

The data model should simply make ordered progressive hints possible.

════════════════════════════════════════════════════
13 — EXAMPLES / COUNTEREXAMPLES
════════════════════════════════════════════════════

EXAMPLE and COUNTEREXAMPLE must remain distinct types.

This is important for future remediation.

A COUNTEREXAMPLE may be used to clarify a knowledge boundary or correct a
conceptual misconception.

Multiple examples/counterexamples may exist.

They must be independently editable, orderable, approvable, and
optionally cognitive-level-specific.

════════════════════════════════════════════════════
14 — RESOURCES
════════════════════════════════════════════════════

RESOURCE must support the content currently practical for this codebase.

Before adding schema, inspect whether existing resource/material
structures already exist.

Prefer reuse.

A resource may conceptually represent:

- teacher note
- supplemental text
- diagram/image reference
- external or internal material reference
- approved supporting material

Do NOT build a full media asset management system in this package.

Do NOT introduce external upload infrastructure unless already available
and directly reusable.

For now implement the minimum durable representation needed by the
existing app.

════════════════════════════════════════════════════
15 — EXERCISES / TASKS — IMPORTANT BOUNDARY
════════════════════════════════════════════════════

Do NOT move exercises into the Teaching Package table merely because
exercises are pedagogical material.

The project already has:

lesson_exercises
lesson_node_cognitive_tasks

and existing MicroNode/Cognitive Level task linkage.

Preserve those as the canonical task/exercise system.

Teaching Package and Exercises are related but distinct.

Conceptually:

MicroNode
├── Teaching Package
│   ├── explanation
│   ├── examples
│   ├── misconceptions
│   ├── hints
│   └── resources
│
└── Tasks / Exercises
    └── existing exercise/task architecture

Later Mapping UI may DISPLAY them together under the same MicroNode.

But do not merge their persistence models.

════════════════════════════════════════════════════
16 — FUTURE BOUNDED VARIANT SUPPORT
════════════════════════════════════════════════════

We have a frozen product requirement:

When approved exercises/material are exhausted or more equivalent
practice is required, future AI may create a bounded equivalent variant.

For exercises this may mean, for example:

same structure / same learning intent / same cognitive demand
with changed numbers, names, or surface details,
but no substantive curriculum change.

DO NOT implement runtime generation now.

However, avoid a data design that makes future provenance impossible.

Future generated variants must be able to trace back to their approved
parent/template.

If a minimal nullable parent/reference field is clearly appropriate and
consistent with current architecture, it may be added.

Do not build the generation engine.

17 — EXISTING CONTENT MIGRATION / SEEDING
════════════════════════════════════════════════════

Teaching Package types.

existing known misconception data
→ MAY seed MISCONCEPTION

existing child-friendly explanation
→ MAY seed MAIN_EXPLANATION or ALTERNATIVE_EXPLANATION depending on
semantics

But this must be evidence-based.

Rules:

1. Preserve original fields during compatibility period.
2. Preserve provenance.
3. Do not silently approve uncertain mappings.
4. Avoid duplicate items when migration/backfill is rerun.
5. Make backfill idempotent where possible.
6. Do not remap/recreate MicroNodes.
7. Do not change existing exercises.

If semantic mapping is uncertain:
leave it untouched and report it.
