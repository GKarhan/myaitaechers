AI TEACHER V2 — ROUND 1
CANONICAL TEACHING STATE MACHINE + SESSION START + SINGLE ACTIVE TASK

IMPORTANT:
This is Round 1 of the AI Teacher V2 rebuild.

The goal is NOT to redesign the whole AI Teacher in one pass.
The goal is to make the teaching runtime deterministic and establish
the canonical orchestration foundation on which later rounds will build.

DO NOT begin by editing code.

First perform the mandatory audit described below and report the actual
current architecture. Then implement only the minimum changes required
for this Round 1.

============================================================
0. LOCKED PRODUCT DECISION — CANONICAL AI TEACHER V2 CONTRACT
============================================================

The following product behavior is now LOCKED.

The AI Teacher must actively lead the lesson.

The learner must NOT need to type:
- "շարունակենք"
- "անցնենք դասին"
- "հաջորդը"
- "օկ" repeatedly
or similar progression commands just to make teaching continue.

However:

When the AI Teacher has issued an assessable question/task,
the teacher MUST stop and wait for the learner's response.

Canonical principle:

NO WAITING FOR PROGRESSION COMMANDS.
WAIT ONLY WHEN REAL LEARNER INPUT IS REQUIRED.

The backend is the teaching orchestrator.

Backend = controls state/progression.
AI = generates/explains/evaluates pedagogical content within backend constraints.
Frontend = renders the current learning/task state.

The AI must NOT independently decide that a MicroNode or Lesson is completed.

============================================================
1. LOCKED HIGH-LEVEL TEACHING FLOW
============================================================

Canonical conceptual flow:

LESSON INTRO
    ↓
MICRONODE START
    ↓
TEACH
    ↓
MICRO_CHECK
    ↓
WAIT_FOR_ANSWER
    ↓
FEEDBACK
    ↓
BACKEND DECISION
    ↓
one of:
    TEACH_MORE
    REMEDIATE
    NEW_MICRO_CHECK
    EXERCISE
    COMPLETION_CANDIDATE

Later rounds will deepen this.

For Round 1, the essential runtime invariant is:

TEACH
→ exactly ONE active task/question
→ WAIT
→ learner response
→ FEEDBACK
→ no second question inside that same feedback turn
→ backend prepares/advances the next state.

============================================================
2. CRITICAL SINGLE-ACTIVE-TASK INVARIANT
============================================================

At any moment, a lesson session may have:

0 active assessable tasks

OR

exactly 1 active assessable task.

Never more than 1.

An active task may eventually be:
- micro-check
- source exercise
- generated equivalent task
- cognitive evidence task

But Round 1 should work with the task types already supported by the repo.
Do NOT invent the future task architecture unless required to fix a proven
current blocker.

When a task is active:

1. The AI must not issue another task.
2. The current task remains open until resolved by the teaching runtime.
3. Help must refer to that same task.
4. The learner response must be evaluated against that same task.
5. Refresh/reload must not lose the active-task state.
6. Repeated messages such as "շարունակենք" must not silently create
   additional concurrent tasks.

IMPORTANT:
Do NOT implement the full intent router in this round.
That is V2-R2.

Only make the state machine safe enough that progression cannot create
multiple simultaneous questions/tasks.

============================================================
3. LESSON INTRO — EXACTLY ONCE PER LESSON SESSION
============================================================

Audit the current greeting/start behavior.

We have already observed runtime behavior such as:

AI:
"Բարև..."
lesson goal/outcomes...
"Եթե պատրաստ ես սկսելու, գրիր՝ Օկ"

Learner:
"օկ"

AI greets again.

Learner:
"օկ"

AI greets again.

This must stop.

Desired behavior:

On a NEW lesson session:

A. Show/produce the lesson introduction once.
B. Introduce:
   - lesson title
   - concise lesson goal
   - concise expected outcome(s)

C. The learner may perform ONE initial start action if the current UI/runtime
   requires it.

After the lesson has started:

- never repeat the initial greeting automatically;
- never ask the learner to repeatedly confirm readiness;
- never require "օկ" to advance normal teaching;
- immediately enter the current MicroNode teaching flow.

Refresh must not cause the intro to restart if the session has already begun.

DO NOT solve this only with prompt wording.
There must be persistent/runtime state that distinguishes:
"lesson not started"
from
"lesson already started".

Use existing schema/state if a correct field already exists.
Do not add duplicate state unnecessarily.

============================================================
4. MICRONODE START
============================================================

When entering a MicroNode, the system must know at minimum:

- lesson
- current MicroNode
- MicroNode title
- learning objective
- mapped/source theory/content
- exercises associated with the MicroNode
- existing teaching content if applicable
- current teaching stage
- current active task, if any

The learner-facing flow should conceptually communicate:

"Hիմա սովորում ենք՝ {MicroNode title}"

and

"Այս մասի նպատակը՝ {learner-friendly learning objective}"

IMPORTANT:
Round 1 does NOT require the final redesigned green UI block.
That comes in a later UI round.

But the backend/API must expose enough canonical current-state information
for the frontend to render it later without reconstructing it from chat text.

Audit what is already exposed before adding anything.

============================================================
5. TEACH STAGE
============================================================

TEACH means:

The AI Teacher teaches the CURRENT MicroNode only.

It may use:

- approved mapped theory/content
- learning objective
- approved additional teaching content
- source examples
- relevant existing exercise context where appropriate

Node Lock remains mandatory.

No teaching from another MicroNode unless the backend explicitly transitions.

Teaching should be broken into learner-friendly chunks rather than a giant
wall of text.

However, do NOT attempt to redesign the complete teaching-content generator
in Round 1.

The important Round 1 behavior is:

After a teaching chunk, the system itself progresses toward a micro-check.

The learner must NOT need to say:
"շարունակենք"
or
"անցնենք առաջ".

============================================================
6. MICRO-CHECK STAGE
============================================================

A micro-check is ONE small diagnostic task.

Existing rule remains:

- one micro-check at a time
- concise
- evidence strength capped at MODERATE
- not sufficient by itself to become STRONG evidence

When the AI emits the micro-check:

the backend/session must persist enough identity to establish:

THIS is the single current active task.

Audit the existing Phase 2B active-task fields before changing schema.

We already introduced concepts such as:

- activeTaskProvenance
- activeHelpCount
- active task/session hydration
- hasActiveTask

DO NOT build a second parallel active-task system.

Reuse and normalize the existing one if possible.

============================================================
7. WAIT_FOR_ANSWER — HARD GATE
============================================================

Once an assessable micro-check/task exists:

the teaching runtime enters a hard waiting state.

While waiting:

- do NOT automatically teach another chunk;
- do NOT generate another question;
- do NOT advance MicroNode;
- do NOT complete MicroNode;
- do NOT silently replace the active task.

The next learner message is handled against the current active task.

Full intent classification is NOT part of R1.
That is R2.

For now, preserve compatibility with existing behavior while ensuring
the state machine does not generate concurrent questions.

============================================================
8. FEEDBACK MUST NOT CONTAIN THE NEXT QUESTION
============================================================

This is a critical V2 invariant.

Current behavior/prompt logic may allow:

learner answers
→ AI gives feedback
→ AI immediately asks another question in the SAME assistant message.

That must stop.

For an evaluated answer:

Assistant turn N = FEEDBACK ONLY.

Feedback may include:

- whether the learner's reasoning was correct/incorrect;
- concise explanation;
- correction;
- remediation explanation;
- encouragement.

But it MUST NOT append the next assessable question/task.

Forbidden pattern:

"Ճիշտ է...
Հիմա պատասխանիր՝ ...?"

Forbidden pattern:

"Սխալ է...
Փորձիր սա՝ ...?"

if the second sentence creates the next assessable task.

The next task must be created only after the backend has completed the
feedback transition and selected the next pedagogical action.

This separation must be represented in runtime state,
not merely requested in prompt prose.

============================================================
9. FEEDBACK → NEXT ACTION
============================================================

After feedback, the backend determines/prepares the next state.

Round 1 does NOT need the final full pedagogical decision engine.
That is V2-R3.

But the architecture must already prevent the AI from arbitrarily chaining
multiple teaching actions in one response.

Reuse the existing:

- teaching cycle logic
- nodeTeachingStage
- validators
- completion logic
- error taxonomy/action machinery

where appropriate.

Do not create duplicate competing systems.

For this round, make the smallest coherent state-machine correction that
establishes deterministic turn boundaries.

============================================================
11. SESSION PERSISTENCE / REFRESH
============================================================

The teaching state must survive page refresh.

Audit current lesson_sessions fields and any chat/session-state endpoint.

After refresh the system must recover:

- current lesson/session
- current MicroNode
- current teaching stage
- whether lesson intro already happened
- whether an active task exists
- current active-task identity/context
- current help level/count where already supported

Refresh must NOT:

- greet again;
- reset the node to THEORY incorrectly;
- duplicate a question;
- generate a second active task;
- lose Help linkage.

If existing state already supports this, reuse it.

16. IMPLEMENTATION PRINCIPLES
============================================================

Prefer:

- deterministic backend transitions
- explicit state
- single source of truth
- minimal schema changes
- reuse of existing session fields
- atomic DB updates where multiple state fields must move together
- strict backend guards
- AI constrained to the current backend-selected action

Avoid:

- adding more prompt prose to compensate for missing state;
- frontend-only flags for authoritative teaching state;
- parsing assistant text to infer current state;
- duplicate state machines;
- duplicate active-task concepts;
- silent fallback that bypasses the canonical cycle.

If the existing enum/stage names can be safely reused, reuse them.

If the current stage model is insufficient, first prove exactly why,
then make the smallest migration/change possible.
