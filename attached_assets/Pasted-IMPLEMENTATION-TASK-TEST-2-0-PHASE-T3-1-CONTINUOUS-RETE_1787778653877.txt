============================================================
PART 1 — CORE PRODUCT MODEL
============================================================

The learner must NOT experience every retest as a separate independent quiz.

The teacher assigns ONE quiz.

That assigned quiz becomes the root of one continuous learner testing session.

Conceptually:

Teacher Quiz / Assignment
    ├── Attempt 1
    ├── Attempt 2
    ├── Attempt 3
    └── ...

The learner dashboard must continue to show ONE teacher-assigned quiz item,
not a new dashboard quiz card for every retest.

Opening that quiz should allow the learner to see its current state/history.

Do NOT create duplicate learner-dashboard assignments merely because the learner
chooses to continue practicing/retesting.

If the current schema already supports multiple attempts under the same quiz
or assignment, reuse it.

Do not create a parallel duplicate quiz architecture unless absolutely required.

PART 2 — ONLY TWO LEARNER STATES INSIDE THIS TEST SESSION
============================================================

For this Test 2.0 continuation experience, simplify the learner-facing state.

Show only:

1. Գիտի
2. Սովորելու

learningNodeIds =

IMPORTANT:

The UI simplification from 4 Knowledge Tree states to 2 Test-session states
must be a projection only.

============================================================
PART 7 — CALCULATION / PROBLEM QUESTIONS NEED SOLUTION EVIDENCE
============================================================

For a simple conceptual multiple-choice question, a short explanation is enough.

Example:

Question:
Ո՞ր թվերն են զույգ։

Correct answer:
2-ի բաժանելիս մնացորդը 0 է։

Explanation:
Զույգ թվերը 2-ի բաժանվում են առանց մնացորդի։

But for a calculation/problem question, displaying only the final numeric
answer is NOT sufficient educational feedback.

Example:

Question:
4000-ը 72-ի բաժանելիս ի՞նչ մնացորդ է ստացվում։

Do not teach only:

Ճիշտ պատասխանը՝ 40։

Prefer a short solution/evidence such as:

72 × 55 = 3960
4000 − 3960 = 40

Ուրեմն մնացորդը 40 է։

The purpose is:

the learner should see WHY the answer is correct,
not memorize an arbitrary number.

IMPORTANT:

Reuse existing explanation/solution data if already available.

Do not introduce a full AI Teacher generation pipeline here.

If current quiz generation already produces whyCorrect / whyWrong /
solution/explanation fields, preserve and surface them appropriately.

If the current data model cannot distinguish a calculation solution from a
simple explanation, inspect first and implement the smallest backward-compatible
extension.

Do not fabricate mathematical solution steps client-side.

============================================================
PART 8 — REPEATED QUESTION BEHAVIOR
============================================================

For this phase, DO NOT build a new Question Engine.

Do NOT dynamically rewrite every question.

Do NOT generate equivalent-number variants yet.

It is acceptable for the same question to appear again in a later attempt.

However, for multiple-choice questions:

shuffle answer option positions on a new attempt.

Hard requirements:

- the semantic correct answer must remain correct
- correctness must not depend on old A/B/C/D position
- stored learner answer and Results rendering must remain accurate
- feedback must point to the correct shuffled option
- shuffling must occur per attempt, not mutate the canonical source question

Example:

Attempt 1:
A wrong
B correct
C wrong
D wrong

Attempt 2 may render:

A wrong
B wrong
C wrong
D correct

but the underlying semantic answer is unchanged.

Do not alter the canonical question merely to shuffle presentation order.
