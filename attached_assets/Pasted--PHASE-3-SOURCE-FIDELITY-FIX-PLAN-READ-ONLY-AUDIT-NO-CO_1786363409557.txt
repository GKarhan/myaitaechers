# PHASE 3 — SOURCE FIDELITY FIX PLAN

## READ-ONLY AUDIT — NO CODE CHANGES YET

Մենք ավարտել ենք Phase 3 forensic audit-ը։

Audit-ի արդյունքով հայտնաբերվել են հետևյալ խնդիրները.

### CRITICAL

**C1 — Coverage completion gate**

`coverageValidation.valid === false` դեպքում mapping job-ը դեռ ստանում է:

```text
status = "completed"
```

Սա սխալ է։

Եթե source coverage-ը incomplete է, mapping-ը չպետք է համարվի fully completed։

---

**C2 — Teacher UI mapping status**

Teacher UI-ն օգտագործում է մոտավորապես.

```ts
const isMapped =
  Boolean(lesson.coreIdea) ||
  ((lesson.nodeCount ?? 0) > 0);
```

Այսինքն՝ incomplete mapping-ը կարող է UI-ում երևալ որպես normal mapped lesson։

---

### HIGH

**H1 — Երկու տարբեր coverage metric**

Validator-ը հաշվում է իրական coverage-ը.

```text
coveredBlocks / totalBlocks
```

իսկ mapping report-ը օգտագործում է այլ բան.

```text
(totalBlocks - unmappedBlocks) / totalBlocks
```

Սա պետք է վերացվի։

Պետք է լինի մեկ canonical coverage metric։

---

**H2 — Raw Pass-1 blocks չեն պահպանվում**

Pass 1-ի source blocks-ը DB-ում ամբողջությամբ չեն պահպանվում։

Եթե հետագայում missing block կա, մենք կարող ենք տեսնել միայն index-ը, բայց ոչ տվյալ block-ի ամբողջ sourceText / page / blockType metadata-ն։

---

**H3 — Exercise source traceability**

`lesson_exercises`-ում `sourceBlockIndex` չկա։

Այս պատճառով DB-ից հետո հնարավոր չէ վստահորեն կառուցել.

```text
Textbook source block
        ↓
Exercise
        ↓
MicroNode
```

# Քայլ 2 — Verify each proposed fix against the actual codebase

Յուրաքանչյուր խնդրի համար ուսումնասիրիր իրական repository-ն և որոշիր.

### P3.1 — Coverage Completion Gate

Գտիր՝

* որտեղ է հաշվարկվում `coverageValidation`
* որտեղ է mapping job-ի վերջնական `status`-ը դրվում
* ինչ status values է իրականում թույլ տալիս schema-ն
* կա՞ `failed`, `needs_review`, կամ այլ համապատասխան status
* ինչ է տեղի ունենում incomplete mapping-ի դեպքում
* կա՞ frontend/backend dependency, որը կարող է կոտրվել status-ի փոփոխությունից

Առաջարկիր **ամենափոքր անվտանգ փոփոխությունը**։

Մի ստեղծիր նոր status, եթե existing status-ով հնարավոր է ճիշտ լուծել խնդիրը։

### P3.3 — Source Block Traceability

Ուսումնասիրիր՝ որտեղ և ինչպես է ստեղծվում Pass-1 `Pass1Block[]`։

Պետք է գնահատել երկու տարբերակ.

**Option A**
Պահպանել source block metadata-ն `mapping_jobs.result`-ում։

**Option B**
Ստեղծել համապատասխան DB table/source-block persistence։

Ընտրիր **ամենափոքր փոփոխությունը, որը բավարարում է forensic traceability-ի պահանջը**։

Պարտադիր չէ ամբողջ source block schema կառուցել, եթե դրա կարիքը չկա։

Պետք է հնարավոր լինի հետագայում missing index-ի դեպքում ստանալ առնվազն.

```text
blockIndex
blockType
sourceText
sourcePage
sourceParagraph
sourceBoundingBox
```

և հասկանալ՝ ինչ textbook content էր կորել։
