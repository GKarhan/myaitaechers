============================================================
PART 1 — CORE PRODUCT RULE
============================================================

AI Teacher must NOT create an unlimited lesson.

A required learning session must have a predictable learning budget.

The system's goal is NOT:

"finish every MicroNode and reach every target cognitive level regardless
of time."

The goal is:

"within the available learning budget, produce the highest-value,
valid learning and evidence possible without trapping the learner in
an endless remediation loop."

There are TWO distinct budgets.

A. SESSION BUDGET
Total required learning time available for the lesson/session.

Example:
20 minutes
25 minutes
30 minutes

B. LOCAL EFFORT BUDGET
How much of that session is reasonable to spend on the current
MicroNode / cognitive level before deferring it.

These are related but NOT identical.

============================================================
PART 2 — REQUIRED SESSION VS OPTIONAL LEARNING
============================================================

The architecture must distinguish:

REQUIRED SESSION

from

OPTIONAL CONTINUATION.

Example:

Teacher assigns 25 minutes.

Student completes 25 minutes of required learning.

The required session can end even if the entire lesson curriculum
has not reached every target cognitive ceiling.

Then UI may offer:

[Ավարտել]
[Շարունակել կամավոր]

If learner continues voluntarily, that learning is valid and its
evidence is valid.

But the system must be able to distinguish required workload from
optional continuation.

Audit where this state should live.

Do NOT implement yet.

============================================================
PART 3 — TIME LIMIT IS NOT FAILURE
============================================================

This invariant is mandatory.

If the session budget expires before a cognitive level is evaluated:

DO NOT record that cognitive level as failed.

Example:

Target:
remember → understand → apply

Student demonstrated:
remember ✓
understand ✓

Session expires before Apply is attempted.

Correct semantic state:

demonstrated = understand
apply = NOT YET EVALUATED / DEFERRED DUE TO SESSION LIMIT

Incorrect:

apply = failed

Similarly:

TIME_BUDGET_EXHAUSTED
must not fabricate negative evidence.

Determine whether the existing evidence/state model can represent this
cleanly or whether a minimal explicit reason/state is needed.

============================================================
PART 4 — LOCAL MICRONODE EFFORT BUDGET
============================================================

A single difficult MicroNode must not consume the entire lesson merely
because MAX_REMEDIATION_STEPS has not been reached.

Example:

Session budget = 25 minutes.

Student has already spent 9 minutes on MicroNode B.
Progress is weak.
Several MicroNodes remain.
Only 8 minutes remain in the required session.

The system should be capable of deciding:

STOP_LEVEL_AND_REVISIT

instead of blindly consuming every remaining remediation step.

IMPORTANT:

Do NOT invent arbitrary production thresholds in this design pass.

First determine what data currently exists.

Report what minimal measurements would be required for a future
decision such as:

continue current level
vs
defer current level
vs
advance
vs
end required session.

============================================================
PART 5 — TIME ACCOUNTING SEMANTICS
============================================================

We need to avoid naive elapsed-clock bugs.

Audit and propose semantics for:

SESSION ELAPSED TIME

versus

ACTIVE LEARNING TIME.

Example:

Student opens the lesson, leaves the browser open for 40 minutes,
then returns.

That must NOT automatically mean the student actively studied for
40 minutes.

Investigate whether current architecture has enough signals to
distinguish active learning from idle wall-clock time.

Consider existing chat/task interactions.

Do NOT build an elaborate attention tracker.

Propose the minimum safe V1 semantics.

Possible options to evaluate include:

- wall-clock session time,
- turn-based active intervals,
- capped inter-turn intervals,
- explicit pause/resume,
- client heartbeat,
- combinations.

Compare trade-offs.

We need a design that is simple enough for R4 but does not make
obviously false time claims.

============================================================
PART 8 — INTERACTION WITH REMEDIATION
============================================================

Current R3 remediationStep is bounded by MAX_REMEDIATION_STEPS.

Design the future decision ordering.

We need to know whether the logic should conceptually behave like:

1. Evaluate valid evidence.
2. Check whether cognitive level is confirmed.
3. If not confirmed, determine whether continued remediation is still
   pedagogically/time-budget appropriate.
4. If yes → remediation.
5. If no → defer/revisit.
6. If overall required session budget is exhausted → end required session.

But inspect actual R3 engine ordering before approving this.

Important:

MAX_REMEDIATION_STEPS remains a HARD SAFETY CEILING.

Learning Budget may stop remediation EARLIER.
