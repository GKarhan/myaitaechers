AI TEACHER V2 — ROUND 2
STUDENT INTENT & RESPONSE ROUTER

============================================================
0. PURPOSE
============================================================

V2-R1 established the backend-controlled teaching foundation:

- one current MicroNode
- one teaching stage
- at most one active task
- one question at a time
- feedback separated from next question
- active task persisted
- session state survives refresh

V2-R2 now solves the next architectural problem:

NOT EVERY STUDENT MESSAGE IS AN ANSWER.

The backend must classify the learner's intent BEFORE allowing
answer evaluation, evidence writing, attempt increments, or
teaching-state progression.

LOCKED PRINCIPLE:

STUDENT MESSAGE
→ INTENT ROUTER
→ permitted action for current backend state
→ only then AI pedagogical processing if needed

Do NOT redesign V2-R1.

============================================================
1. CURRENT PROBLEM
============================================================

Current runtime historically treated messages such as:

"օկ"
"լավ"
"շարունակենք"
"արի շարունակենք"
"չգիտեմ"
"դու ասա"
"օգնի"
"չեմ հասկանում"
"կրկնի"
"ուրիշ օրինակ տուր"

through the same AI evaluation path used for real learner answers.

This creates risks:

- fake answer attempts
- fake evidence
- progression commands skipping active tasks
- confusion/help requests being marked incorrect
- unnecessary AI calls
- safety-cap counters increasing incorrectly

V2-R2 must separate these semantics.

============================================================
2. CANONICAL INTENT CONTRACT
============================================================

Implement these canonical intent classes:

ANSWER
READY
CONTINUE
HELP
CONFUSED
REPEAT
CLARIFY
OFF_TOPIC

Optionally:

OTHER

only if genuinely necessary.

Definitions:

ANSWER
A genuine attempt to answer the currently active assessable task.

READY
Acknowledgement/start signal:
"օկ", "լավ", "պատրաստ եմ"

CONTINUE
Progression request:
"շարունակենք", "անցնենք առաջ", "հաջորդը"

HELP
Explicit help request:
"օգնի", "օգնություն", "հուշում տուր"

CONFUSED
Learner cannot answer / does not understand:
"չգիտեմ"
"չեմ կարող"
"չեմ հասկանում"
"դու ասա"

REPEAT
Request to repeat/rephrase current explanation/task:
"կրկնի"
"նորից ասա"
"կրկին բացատրի"

CLARIFY
Learner asks clarification about current MicroNode/task.

OFF_TOPIC
Learner requests another lesson/topic or unrelated content.

============================================================
3. IMPORTANT — INTENT IS STATE-AWARE
============================================================

The same message can mean different things depending on state.

Example:

"օկ"

During INTRO_WAITING:
→ READY

During CHECK_WAITING:
→ NOT an ANSWER
→ acknowledgement/non-answer

During ordinary TEACH with no input required:
ideally learner should not need to send it at all.

"շարունակենք"

With NO active task:
→ CONTINUE may be harmless, though auto-progression should normally
  make it unnecessary.

With active task:
→ MUST NOT skip the task.

Therefore the router must receive:

- current teaching state
- hasActiveTask
- active task type
- current MicroNode
- intro state

Do NOT classify text in isolation.

============================================================
4. TWO-STAGE CLASSIFICATION STRATEGY
============================================================

Prefer:

STAGE A — deterministic classification

Use deterministic normalization/rules for obvious cases:

READY
CONTINUE
HELP
CONFUSED
REPEAT

Examples:
exact/short phrase matching,
normalized Armenian punctuation/spacing,
known variants.

STAGE B — contextual AI classification only when needed

Use AI only for ambiguous cases such as:

ANSWER vs CLARIFY vs OFF_TOPIC

Do NOT send every trivial "օկ" through the main teaching model.

If AI classification is required:
use a small structured classification contract.

It must NOT generate teaching content.

Output only the intent classification.

============================================================
5. ARMENIAN NORMALIZATION
============================================================

Audit current normalization utilities before creating new ones.

Handle common variants safely:

- Armenian punctuation
- extra spaces
- capitalization
- repeated punctuation
- simple transliterated "ok" if currently supported
- common spelling variants

Do not build a giant NLP system.

Use deterministic normalization where practical.

============================================================
6. ROUTING CONTRACT
============================================================

After intent classification:

READY:
- only meaningful for lesson/session start
- must not become answer evidence

CONTINUE:
- if active task exists:
  keep same task
  do not progress
  return appropriate learner-facing response / expose Help
- if no active task:
  do not create fake evidence

HELP:
- route to structured Help flow
- same active task
- no answer evidence
- no attempt increment

CONFUSED:
- keep same active task
- do not mark incorrect automatically
- do not create answer evidence
- prepare remediation/help path

REPEAT:
- repeat/rephrase current explanation/task
- do not create evidence
- do not increment attempt
- do not create new task identity

CLARIFY:
- answer within CURRENT MicroNode/task scope
- preserve active task
- do not treat clarification request as task answer

OFF_TOPIC:
- use existing Node Lock redirect behavior
- no evidence
- no progression

ANSWER:
- ONLY this path may enter assessable-answer evaluation
- may update attempt sequence
- may create evidence
- may enter FEEDBACK state

============================================================
7. ACTIVE TASK HARD RULE
============================================================

If hasActiveTask = true:

Only ANSWER may resolve/evaluate that active task.

READY / CONTINUE / HELP / CONFUSED / REPEAT /
CLARIFY / OFF_TOPIC:

must leave the same task active.

Do NOT clear:

- active task identity
- lessonExerciseId
- cognitiveLevelId
- help state
- lastQuestionAsked

unless the existing Help semantics explicitly update help metadata.

============================================================
8. "ՉԳԻՏԵՄ" IS NOT INCORRECT EVIDENCE
============================================================

LOCKED PRODUCT RULE:

A learner explicitly saying:

"չգիտեմ"
"չեմ կարող"
"դու ասա"

means the learner did NOT produce an assessable answer.

Therefore:

- no incorrect answer evidence
- no mastery penalty in this Round
- no attempt increment as a submitted answer
- active task remains open

The system may respond with:
- Help
- simpler explanation
- hint
- guided support

But that response belongs to pedagogical remediation,
not answer scoring.

============================================================
9. CONTINUE CANNOT SKIP A TASK
============================================================

With active task:

Student:
"շարունակենք"

Expected:

Do NOT:
- clear task
- move to next task
- move MicroNode
- mark answer incorrect
- increment attempt

Instead communicate naturally that the current task is still active
and optionally offer Help.

No progression bypass.

============================================================
10. HELP TEXT AND HELP BUTTON MUST CONVERGE
============================================================

We already have structured:

💡 Օգնություն

backend/help infrastructure.

Text-based messages such as:

"օգնի"
"օգնություն"
"հուշում տուր"

should route to the SAME structured Help mechanism where possible.

Do NOT maintain two unrelated help systems:

A. button Help
B. ordinary AI chat help

Both should eventually produce the same:

active task
→ help event
→ assistance level
→ same task remains open

Do NOT redesign progressive help levels in this Round.

Reuse Phase 2B infrastructure.

============================================================
11. CLARIFICATION WHILE TASK ACTIVE
============================================================

Example:

Task:
"Ո՞րն է մոլեկուլի տարբերությունը ատոմից։"

Student:
"իսկ ատոմը ինչ է նշանակում?"

This is CLARIFY, not ANSWER.

Expected:

AI can answer the clarification briefly within Node Lock.

Then:

the SAME original active task remains open.

Do not generate a replacement question unless backend later decides so.

============================================================
12. REPEAT REQUEST
============================================================

Example:

"կրկնի"
"նորից բացատրի"

If active task:
repeat/rephrase the same task or relevant explanation.

If no active task:
repeat/rephrase the current teaching chunk.

Do not create evidence.

Do not change stage unnecessarily.

============================================================
13. OFF-TOPIC / NODE LOCK
============================================================

Reuse existing:

redirect_needed
validateNodeLock
scope-drift protections

Do not build another competing Node Lock.

The intent router should only identify OFF_TOPIC and then invoke the
existing authoritative redirect behavior.

No evidence from off-topic requests.

============================================================
14. ANSWER DETECTION
============================================================

Do NOT use simplistic:

"anything not in phrase list = ANSWER"

For active tasks, genuine answers may include:

- one word
- a number
- a selected option
- a short sentence
- a longer explanation

The router must use task context where necessary.

Examples:

Task:
"2 + 2 = ?"

Student:
"4"
→ ANSWER

Task:
"Ո՞րն է ճիշտ տարբերակը՝ A, B, թե C"

Student:
"B"
→ ANSWER

Task:
"Բացատրի՛ր տարբերությունը"

Student:
"մոլեկուլը կազմված է ատոմներից"
→ ANSWER

Task:
same

Student:
"չգիտեմ"
→ CONFUSED

============================================================
15. STRUCTURED INTENT RESULT
============================================================

Create/reuse a typed contract such as:

{
  intent:
    "ANSWER"
    | "READY"
    | "CONTINUE"
    | "HELP"
    | "CONFUSED"
    | "REPEAT"
    | "CLARIFY"
    | "OFF_TOPIC"
    | "OTHER",

  confidence?: number,
  reason?: string
}

Internal shape may differ.

Do NOT expose model reasoning to learner.

Prefer deterministic intent results where possible.

============================================================
16. INTENT MUST BE OBSERVABLE
============================================================

For debugging/testing, the backend should be able to log safely:

- sessionId
- current state
- hasActiveTask
- classified intent
- routing decision

Do not log sensitive unnecessary student information.

Do not show debug fields in production learner UI.

============================================================
17. EVIDENCE GATE
============================================================

Before any AI Teacher evidence write:

require:

intent === ANSWER

AND

active assessable task exists

AND

answer evaluation produced valid evidence quality.

This is a HARD backend gate.

No AI output may override it.

Therefore:

READY
CONTINUE
HELP
CONFUSED
REPEAT
CLARIFY
OFF_TOPIC

must never directly produce answer evidence.

============================================================
18. ATTEMPT COUNTER GATE
============================================================

Attempt counters must increment only for actual assessable ANSWER
submissions.

Do NOT increment for:

- READY
- CONTINUE
- HELP
- CONFUSED
- REPEAT
- CLARIFY
- OFF_TOPIC

This also prevents artificial safety-cap progression.

============================================================

Only make frontend changes required to:

- route structured Help if needed
- preserve active task
- display appropriate returned message
- prevent accidental double submission
