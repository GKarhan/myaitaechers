1. KEY PRODUCT RULE
==================================================

Draft authoring may temporarily be incomplete.

Example:

teacher creates first level
→ no target yet
→ still allowed as DRAFT / NEEDS_REVIEW

But a path must NOT become:

CONFIRMED / ACCEPTED / READY

unless it passes the SAME canonical runtime Cognitive Path contract.

Therefore distinguish:

A. editable draft/review state
B. confirmed/accepted state

Do NOT prevent all partial editing.

Do prevent invalid paths from being confirmed.

==================================================
3. CONFIRMATION MUST FAIL CLOSED
==================================================

When teacher attempts to confirm/approve a Cognitive Path, require:

1. At least one applicable Cognitive Level.
2. Exactly one applicable isTargetCeiling=true.
3. Target is applicable.
4. Target is the final ordered applicable level.
5. Sequences are valid/contiguous according to existing path contract.
6. Cognitive/Bloom progression is strictly increasing.
7. No duplicate cognitive levels.
8. Required performanceObjective exists.
9. Required successCriterion exists.
10. minimumIndependentEvidence satisfies current contract.
11. preferredInteractionTypes satisfy current contract.
12. grounding/source requirements pass.
13. any other current accepted-path invariant passes.

If not:

- do NOT confirm
- do NOT mark cogPathStatus confirmed
- return machine-readable validation reasons

Do not silently fix semantic structure during confirmation.

==================================================
4. SINGLE-LEVEL PATH MUST BE VALID
==================================================

This is important.

A MicroNode may legitimately have only one cognitive level.

Example:

Understand [target]

This must be confirmable if all other requirements pass.

Do NOT force:

Remember → Understand

or any lower Bloom levels.

Likewise:

Apply [target]

may be valid if that is the intentionally mapped single-level path and the accepted contract permits it.

The authoring system must reflect the mapped curriculum path, not mechanically construct all Bloom levels.

==================================================
5. TARGET INTEGRITY
==================================================

At most one target is already DB-protected, but authoring must enforce the full target contract.

When teacher changes target:

- old target must be cleared atomically
- new target must be applicable
- new target must be final in the confirmed path
- no transient confirmed state with two/no targets

If teacher changes ordering and target is no longer final:

- path must return/remain NEEDS_REVIEW
- it must not stay CONFIRMED

If teacher makes target non-applicable:

- path must return/remain NEEDS_REVIEW
- confirmation must fail until corrected

==================================================
6. COGNITIVE ORDER INTEGRITY
==================================================

Confirmed paths must progress in valid Bloom order.

Examples:

VALID:
Remember → Understand
Understand → Apply
Understand → Apply → Analyze

INVALID:
Apply → Understand
Analyze → Apply
Apply → Remember → Analyze

Do not reorder the teacher's path automatically during confirmation.

Return a clear structural validation reason.

Draft editing may temporarily contain invalid order, but it cannot be confirmed.

==================================================
7. targetBloomLevel COMPATIBILITY COPY
==================================================

Canonical target remains:

lesson_node_cognitive_levels.isTargetCeiling

lesson_nodes.targetBloomLevel is compatibility/derived data only.

Inspect current synchronization behavior.

On successful confirmation:

- synchronize targetBloomLevel from the canonical target level
- do this in the same transaction as confirmation if possible

Do NOT use targetBloomLevel to decide the canonical target.

If path becomes invalid/review-required after an edit:

choose the safest behavior according to current architecture:

- either keep compatibility value but mark path NEEDS_REVIEW,
- or clear it if that is already the established invariant.

Do not invent inconsistent semantics.

Document the chosen behavior.

==================================================
8. MUTATION AFTER CONFIRMATION
==================================================

Any edit to a confirmed Cognitive Path that could affect validity must force revalidation.

Examples:

- cognitiveLevel changed
- sequence changed
- target changed
- applicability changed
- performanceObjective changed
- successCriterion changed
- interaction types changed
- evidence count changed
- level deleted
- new level added

Preferred rule:

confirmed path + structural/semantic edit
→ path becomes NEEDS_REVIEW / unconfirmed
→ teacher must confirm again

unless existing architecture already has a safe equivalent rule.

Do not allow stale CONFIRMED status after meaningful edits.

==================================================
9. DELETE BEHAVIOR
==================================================

Deleting a level must preserve structural safety.

If delete affects:

- target
- final level
- sequence
- confirmed path

then:

- normalize level sequence if existing authoring contract requires it
- path becomes NEEDS_REVIEW
- target invariants must be re-established before reconfirmation

Do not auto-select a new target silently unless this is already canonical behavior.

==================================================
10. REORDER BEHAVIOR
==================================================

Reordering must preserve deterministic sequence values.

After reorder:

- sequence = 1..N
- relative order = requested order
- if confirmed path no longer satisfies cognitive progression/target-final invariant:
  mark NEEDS_REVIEW

Do not silently change cognitiveLevel values.
