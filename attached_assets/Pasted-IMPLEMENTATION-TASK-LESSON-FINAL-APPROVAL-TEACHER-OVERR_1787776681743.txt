IMPLEMENTATION TASK — LESSON FINAL APPROVAL / TEACHER OVERRIDE POLICY

GOAL

Align lesson assignment readiness with the approved product rule:

A lesson should be assignable whenever it is technically safe to deliver.

Pedagogical incompleteness or review findings must be shown clearly to the teacher,
but the teacher must be allowed to explicitly confirm and assign the lesson anyway.

Only true structural/data-integrity failures remain non-overridable BLOCKED states.

This is a SYSTEMIC policy change.

Do NOT special-case Lesson 722.

==================================================
0. PROVEN CURRENT PROBLEM
==================================================

For Lesson 722 — «Մնացորդով բաժանում»:

- mapping completed
- 3 canonical MicroNodes exist
- 4 verified-readable instructional blocks have no canonical MicroNode owner
- final approval currently returns:

HTTP 422
readiness = BLOCKED
code = UNRESOLVED_INSTRUCTIONAL_SOURCE

The established product requirement is different:

This condition must be shown to the teacher as a serious warning,
but the teacher must be able to consciously confirm:

«Այնուամենայնիվ հաստատել և հանձնարարել»

and then the lesson may proceed to approval/activation.

Therefore current final-approval policy is too strict for this class of pedagogical finding.

==================================================
1. REQUIRED READINESS MODEL
==================================================

The authoritative final-approval contract must have three semantic classes:

READY

CONFIRMATION_REQUIRED

BLOCKED

Meanings:

READY
→ no confirmation needed

CONFIRMATION_REQUIRED
→ one or more pedagogical/review findings exist
→ teacher sees them
→ teacher may explicitly accept responsibility
→ lesson can then be approved/activated

BLOCKED
→ technical/structural/data-integrity state makes learner delivery unsafe
→ teacher override is NOT permitted

Do not collapse these states.

==================================================
2. MOVE UNRESOLVED INSTRUCTIONAL OWNERSHIP
==================================================

Change:

UNRESOLVED_INSTRUCTIONAL_SOURCE

from:

hard BLOCKED error

to:

CONFIRMATION_REQUIRED / overrideable finding

when:

- source scope is verified;
- source blocks are readable;
- canonical lesson structure exists;
- at least one valid MicroNode exists;
- the issue is specifically incomplete instructional ownership,
  not source corruption/loss.

The teacher must see the exact safe count.

Example:

«Ընթեռնելի ուսումնական աղբյուրից 4 հատված MicroNode-ի պատասխանատու չունի»։

But this must no longer prevent explicit teacher confirmation.

==================================================
3. WHAT MUST REMAIN HARD BLOCKED
==================================================

Do NOT make everything overrideable.

Keep non-overridable BLOCKED behavior for true unsafe conditions such as:

- unverified lesson source scope;
- missing/corrupt source identity;
- zero canonical MicroNodes;
- invalid/corrupt lesson structure;
- empty MicroNodes where learner delivery has no usable target;
- unsafe or invalid node/source identity;
- broken lesson/course ownership;
- invalid topic/node sequence where runtime assumptions would fail;
- persistence/integrity failures;
- any condition where learner package generation cannot be trusted.

Reuse existing hard blocker codes where available.

Do not invent broad new override permissions.

==================================================
4. CONFIRMATION_REQUIRED FINDINGS
==================================================

The following should remain or become teacher-confirmable under the established product rule:

- unresolved readable instructional source ownership;
- incomplete/unconfirmed Cognitive Paths;
- incomplete Teaching Content;
- Goal/Outcome review findings;
- Outcomes without REQUIRED MicroNode links;
- draft source exercises;
- partial but safe source alignment;
- compound/mega-node advisory findings;
- other pedagogical completeness findings that do not make runtime delivery unsafe.

Do not change their underlying diagnostics.

Only classify them correctly for approval policy.

==================================================
5. AUTHORITATIVE FINAL APPROVAL FLOW
==================================================

Update validateLessonForFinalApproval so it returns conceptually:

READY
→ approved may proceed

CONFIRMATION_REQUIRED
→ HTTP / response contract consistent with existing confirmation flow
→ teacher must explicitly confirm
→ second confirmed request may approve

BLOCKED
→ hard error
→ no override

Reuse the existing confirmation mechanism if one already exists.

Do NOT build a parallel approval system.

==================================================
6. EXPLICIT TEACHER CONFIRMATION
==================================================

The teacher override must be explicit.

The teacher must not accidentally assign merely by clicking once.

For confirmation-required lessons, show a dialog summarizing:

- lesson is not fully ready;
- exact findings;
- which are warnings/review items;
- assignment can still proceed if teacher accepts.

Required actions conceptually:

«Վերադառնալ և ուղղել»

«Այնուամենայնիվ հաստատել և հանձնարարել»

Use existing Armenian UI style.

Do not use developer codes in primary UI text.

Do NOT create a large new audit subsystem if current approval metadata already supports this.
