TASK — DESIGN THE TARGET AUTOMATIC MAPPING ARCHITECTURE
NO CODE CHANGES. NO DATABASE WRITES. NO MAPPING RERUNS.

We have completed the read-only forensic audit of automatic mapping for
lesson 708 / mapping job 174.

Use that audit as evidence, but DO NOT implement fixes yet.

The goal of this task is to design the smallest robust target architecture
for automatic lesson mapping so that the mapper identifies the lesson's
actual atomic knowledge units first, rather than allowing source fragments,
notes, examples, exercises, topic boundaries, or cognitive levels to create
artificial MicroNodes.

════════════════════════════════════════════════════════════════════
0. NON-NEGOTIABLE PRODUCT MODEL
════════════════════════════════════════════════════════════════════

Canonical hierarchy:

Subject → Lesson → Topic → MicroNode

MicroNode is the atomic curriculum knowledge unit.

CORE CONTRACT:

ONE MICRONODE = ONE COHERENT, SOURCE-BACKED,
INDEPENDENTLY TEACHABLE AND ASSESSABLE LEARNING OBJECTIVE.

MicroNode count must NEVER be predetermined.

A lesson may legitimately contain:
- 2 MicroNodes,
- 4 MicroNodes,
- 10 MicroNodes,
- 20 MicroNodes,
or any other number required by the actual source knowledge structure.

Do NOT optimize for fewer nodes.
Do NOT optimize for more nodes.

Optimize for the correct atomic knowledge decomposition.

Important distinction:

WHAT the learner learns
    = MicroNode

HOW DEEPLY the learner learns it
    = Cognitive Path / cognitive levels

Therefore Remember / Understand / Apply / Analyze etc.
must NOT create separate MicroNodes for the same knowledge.

Example:

Knowledge:
"Determine the sign of a rational expression."

This should normally remain ONE MicroNode even if later the learner must:

Remember the rule
→ Understand why it works
→ Apply it
→ Analyze a sign chart

Those are cognitive uses/depths of the same knowledge,
not automatically four knowledge nodes.

1. IMPORTANT PRODUCT DECISION — PRESERVE SOURCE MATERIAL
════════════════════════════════════════════════════════════════════

We do NOT want the mapper to delete or silently discard pedagogically
questionable source material merely because it should not become a MicroNode.

If a source block is structurally safe and source-verified, preserve it.

The teacher should ultimately be able to review questionable material and
decide whether it should:

- remain supporting material,
- attach to another MicroNode,
- become a MicroNode,
- merge with another MicroNode,
- split an existing MicroNode,
- or be excluded from teaching.

Therefore distinguish clearly between:

A. SOURCE PRESERVATION

and

B. MICRONODE PROMOTION.

A block may be preserved without being promoted into a MicroNode.

Do NOT solve the forensic findings by simply deleting NOTE blocks.

════════════════════════════════════════════════════════════════════
2. SOURCE MATERIAL IS NOT THE SAME AS KNOWLEDGE
════════════════════════════════════════════════════════════════════

The source may contain:

- definition
- rule
- explanation
- theorem/property
- example
- counterexample
- note
- hint
- formula
- table
- diagram
- illustration
- worked solution
- exercise
- question
- activity
- summary
- objective
- heading
- continuation text
- OCR/layout noise

These are SOURCE BLOCKS.

They are not automatically MicroNodes.

A source block should create or contribute to a MicroNode only when it
provides evidence for an independently teachable and assessable knowledge
objective.

Otherwise it should normally become one of:

- theory/supporting explanation,
- example,
- counterexample,
- representation,
- hint,
- exercise,
- activity,
- visual/supporting material,
- structural material,
- unresolved/review material.

IMPORTANT:

Do NOT implement a simplistic rule such as:

NOTE → never MicroNode
EXAMPLE → never MicroNode

because a NOTE or EXAMPLE can sometimes contain genuinely new knowledge.

The decision must be semantic and source-backed.

════════════════════════════════════════════════════════════════════
6. DESIGN THE MICRONODE PROMOTION GATE
════════════════════════════════════════════════════════════════════

Define the exact conceptual test for promoting a Knowledge Candidate into a
MicroNode.

A candidate should normally become a MicroNode only if:

A. SOURCE SUPPORT
There is direct, readable source evidence.

B. KNOWLEDGE IDENTITY
The source supports a meaningful knowledge/concept/skill, not merely a
layout fragment or presentation detail.

C. INDEPENDENT TEACHABILITY
The objective can reasonably be taught as a distinct knowledge unit.

D. INDEPENDENT ASSESSABILITY
The learner's knowledge of it can be checked independently.

E. ATOMICITY
It contains one coherent objective rather than multiple independent
objectives.

F. NON-DUPLICATION
It is not semantically the same knowledge as another candidate.

G. SUPPORTING-MATERIAL TEST
If the source is primarily an example, note, hint, diagram, representation,
or continuation of another concept, determine whether it should attach to
that concept instead of becoming a new node.

Design this carefully.

We need semantic judgment, not keyword heuristics alone.

8. LESSON-WIDE DUPLICATE CONSOLIDATION
════════════════════════════════════════════════════════════════════

The audit found cross-topic duplicate risk:

2408 and 2411 represented materially overlapping sign-interval knowledge
but existed in different Topics.

Current high-confidence consolidation does not cross Topics.

Design how semantic identity should work lesson-wide.

Critical principle:

Topic boundaries must organize knowledge.
They must NOT define knowledge identity.

If two candidates represent the same atomic knowledge but occur in
different textbook sections/topics, the mapper should normally create one
MicroNode and preserve both source references.

However:

Do NOT blindly merge similar wording.

Two concepts can have similar vocabulary but represent different knowledge.

Define the distinction between:

- SAME KNOWLEDGE → merge source/support
- RELATED KNOWLEDGE → separate MicroNodes + dependency/relationship
- SAME KNOWLEDGE, DIFFERENT COGNITIVE USE → one MicroNode + Cognitive Path
- SUPPORTING MATERIAL → attach to existing MicroNode
- TRUE INDEPENDENT KNOWLEDGE → separate MicroNode
- UNCERTAIN → preserve both/review safely

14. HARD GATES VS PEDAGOGICAL REVIEW
════════════════════════════════════════════════════════════════════

Preserve the safety policy already implemented.

- invalid source provenance,
- parser/schema corruption,
- broken references,
- impossible source ownership,
- coverage/integrity failure,
- transaction failure.

PEDAGOGICAL UNCERTAINTY should normally:

- persist safely,
- be marked for review,
- not become silently trusted,
- not be bulk-approved/enriched/final-approved while unresolved.

Do NOT weaken any existing integrity gate.

The architecture must clearly separate:

STRUCTURAL SAFETY

from

PEDAGOGICAL QUALITY / UNCERTAINTY.
