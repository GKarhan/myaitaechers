IMPLEMENTATION PHASE 2 — DURABLE SOURCE MATERIAL PRESERVATION

Phase 1 is complete.

We now have the transient internal mapping contracts for:

- KnowledgeCandidate
- SourceMaterialDisposition
- structured promotion decisions
- explicit semantic uncertainty
- deterministic regression coverage

DO NOT implement Candidate-based Pass 2 yet.

This phase solves the next foundational requirement:

EVERY VERIFIED SOURCE BLOCK MUST SURVIVE DURABLY
EVEN WHEN IT DOES NOT BECOME A MICRONODE.

The goal is to make source preservation independent from MicroNode promotion.

This is foundational infrastructure for the final Mapping Contract v2.

════════════════════════════════════════════════════════════
0. CORE ARCHITECTURAL PRINCIPLE
════════════════════════════════════════════════════════════

The mapper must distinguish:

SOURCE PRESERVATION

from

KNOWLEDGE PROMOTION.

A verified textbook/source block must not disappear merely because it:

- is not atomic knowledge,
- is supporting explanation,
- is an example,
- is a note,
- is a visual/formula,
- is structural material,
- is unresolved,
- requires teacher review,
- or is not promoted into a MicroNode.

Canonical principle:

VERIFIED SOURCE BLOCK
        ↓
DURABLE SOURCE MATERIAL
        ↓
PRIMARY DISPOSITION
        ↓
Knowledge Candidate / Supporting / Exercise /
Structural / Unresolved / Review / Excluded
        ↓
possible MicroNode promotion later

MicroNode persistence must NOT be the only durable storage mechanism for
verified source content.

════════════════════════════════════════════════════════════

════════════════════════════════════════════════════════════
3. STABLE IDENTITY
════════════════════════════════════════════════════════════

Current Pass 1 block indices are temporary array positions.

Design a durable identity strategy.

A durable source block must not depend solely on:

blockIndex = 7

because a future remap may produce different array positions.

Determine the smallest safe stable identity based on existing data.

Possible inputs may include:

- lesson id
- source document id
- physical page
- source location
- exact source text
- deterministic hash/fingerprint

But inspect current architecture before choosing.

Requirements:

- deterministic where practical
- collision-safe enough for this use
- traceable
- supports remapping
- does not silently confuse two identical textual occurrences on different
  pages/locations

Do NOT introduce unnecessary complexity.

════════════════════════════════════════════════════════════
4. PRIMARY DISPOSITION CONTRACT
════════════════════════════════════════════════════════════

Every verified source block must eventually have exactly ONE canonical
PRIMARY disposition.

Use/align with Phase 1 SourceMaterialDisposition semantics.

Conceptual primary dispositions include:

CORE_EVIDENCE
SUPPORTING_MATERIAL
EXERCISE
ACTIVITY_OR_HOMEWORK
STRUCTURAL_MATERIAL
UNRESOLVED_VISUAL_OR_FORMULA
UNRESOLVED_INSTRUCTIONAL_REVIEW
EXCLUDED_WITH_REASON

Project-appropriate names may be used if Phase 1 already established them.

IMPORTANT:

Primary disposition is not the same as all semantic relationships.

Example:

A definition block may be:

primary disposition = CORE_EVIDENCE

and later support one promoted MicroNode.

An example block may be:

primary disposition = SUPPORTING_MATERIAL

and later be attached to one or more MicroNodes.

An integrative exercise may be:

primary disposition = EXERCISE

and later reference multiple MicroNodes.

Therefore:

ONE PRIMARY DISPOSITION

does NOT necessarily mean:

ONE SEMANTIC RELATIONSHIP.

Keep those concepts separate.

════════════════════════════════════════════════════════════
5. DO NOT RECREATE THE OLD OWNERSHIP BUG
════════════════════════════════════════════════════════════

We previously had coverage failures because one source block was treated as
being canonically owned simultaneously by:

- sourceBlockIndices
- supportingMaterialIndices
- exercises
- additionalExercises
- unmappedBlockIndices

Do NOT reproduce this architecture in a new form.

The new durable source-material model must clearly distinguish:

CANONICAL PRIMARY DISPOSITION

from

SECONDARY RELATIONSHIPS / ATTACHMENTS.

A block should not become invalid merely because the same supporting
material semantically supports multiple knowledge candidates.

Canonical coverage and semantic relationships are separate concerns.

════════════════════════════════════════════════════════════
6. UNREADABLE / VISUAL / FORMULA MATERIAL
════════════════════════════════════════════════════════════

This is critical.

If a verified source location contains:

- formula
- diagram
- graph
- table
- image
- layout-dependent mathematics
- incomplete OCR/text extraction
- other unreadable instructional content

DO NOT:

- fabricate missing content,
- silently discard it,
- automatically promote it into a MicroNode,
- treat blank/garbled text as trusted knowledge.

Instead preserve the best available provenance and mark the material
explicitly for unresolved/review handling.

The future teacher review system must be able to know:

"There is source material here that automatic semantic mapping could not
safely interpret."

If existing source-page/image provenance can support future visual review,
preserve the required references without implementing the review UI now.

════════════════════════════════════════════════════════════
7. EXCLUDED MATERIAL
════════════════════════════════════════════════════════════

EXCLUDED_WITH_REASON must NOT mean deleted.

If material is intentionally excluded from instructional mapping because it
is, for example:

- page furniture
- repeated heading
- irrelevant structural fragment
- confirmed extraction noise

the durable source record should remain auditable with a machine-readable
reason.

No silent disappearance.

════════════════════════════════════════════════════════════
8. REMAPPING / IDEMPOTENCY
════════════════════════════════════════════════════════════

Design safe remapping semantics.

When the same lesson is automatically mapped again:

- do not accumulate stale duplicate source-material records,
- do not lose current source lineage,
- do not leave orphan relationships,
- do not silently attach new MicroNodes to obsolete source-block identities.

Determine whether source-material persistence should use:

- replace semantics,
- upsert semantics,
- mapping-version semantics,
- or another existing project pattern.

Prefer consistency with the current atomic mapping transaction.

Any source-material replacement must participate safely in the mapping
transaction.

A failed mapping must not destroy the last valid persisted source map.

════════════════════════════════════════════════════════════
9. TRANSACTION / FAILURE SAFETY
════════════════════════════════════════════════════════════

Preserve the existing fail-safe policy.

Hard structural failures still mean NO replacement of the current valid map.

Examples:

- invalid source provenance
- parser/schema corruption
- invalid references
- impossible canonical coverage
- transaction failure

If new source-material persistence is part of successful automatic mapping,
it must be transactionally consistent with the persisted map.

We must never end up with:

new source material + old MicroNodes

or

new MicroNodes + old source material

for what is supposed to be one mapping version.

Explain and enforce the transaction boundary.

════════════════════════════════════════════════════════════
10. TEACHER EDITS
════════════════════════════════════════════════════════════

Teacher edits to MicroNodes must NOT destroy source provenance.

If the teacher later:

- renames a MicroNode
- edits learningObjective
- edits theory
- moves a MicroNode
- merges/splits nodes in a future phase
- excludes a candidate

the underlying durable textbook/source material must remain independently
recoverable.

Source truth and teacher-authored pedagogical structure are separate layers.

Do NOT implement Merge/Split in this phase.

Just ensure this architecture does not make future Merge/Split destructive.
