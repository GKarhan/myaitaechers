1. REQUIRED SYSTEMIC INVARIANT
════════════════════════════════════════════════════

Add a deterministic server-side persistence safety gate.

The mapper MUST NOT publish/replace a lesson's canonical mapping as a
successful zero-MicroNode mapping when the zero-node result is caused by
a batch-level M3-2 technical availability failure.

Specifically, detect the condition where ALL of the following are true:

A. The pipeline discovered one or more viable candidate MicroNodes.

B. M3-2 semantic assessment suffered a batch-level technical/unavailable
   condition, such as provider request failure / retry exhaustion /
   equivalent technical unavailability.

C. There are zero valid semantic decisions for the affected candidate
   population, or the semantic decision layer is otherwise unavailable
   at batch level.

D. Promotion produces zero canonical MicroNodes / zero PROMOTE decisions.

E. The result would otherwise replace or publish the canonical mapping
   with zero MicroNodes.

When this condition is true:

DO NOT persist/publish the new zero-MicroNode canonical mapping.

Fail closed before canonical replacement.

════════════════════════════════════════════════════

The run must become a clearly distinguishable technical review/retry state.

Use the existing mapping-job failure/review architecture if possible.

Do not describe viable candidates as pedagogically invalid merely because
the provider was unavailable.

════════════════════════════════════════════════════

ABSOLUTELY DO NOT solve this by promoting candidates without semantic
validation.

Do NOT:

- auto-PROMOTE because source support is DIRECT;
- auto-PROMOTE because exercises exist;
- auto-PROMOTE because a candidate title looks valid;
- treat MISSING_DECISION as a positive semantic decision;
- bypass atomicity uncertainty;

- downgrade M3-2 fail-closed rules;
- add heuristic promotion fallback.

The correct behavior is:

provider technically unavailable
→ canonical promotion remains fail-closed
→ canonical replacement also becomes fail-closed.

Two safety gates, not one weakened gate.

════════════════════════════════════════════════════
6. DISTINGUISH TECHNICAL FAILURE FROM LEGITIMATE ZERO-NODE RESULTS
════════════════════════════════════════════════════

Do NOT create a simplistic rule:

canonicalMicroNodes.length === 0 → fail

That would be wrong.

A legitimate mapping may theoretically produce zero promotable candidates
because the material genuinely contains no valid instructional knowledge
units.

The new gate must depend on PROVEN TECHNICAL M3-2 UNAVAILABILITY combined
with discovered viable candidate population and zero valid decisions /
zero promotions.

Examples:

CASE A
Candidates = 10
M3-2 decisions = 10 valid
All semantically REJECT/SUPPORT_ONLY
Promotions = 0

→ Do NOT classify as technical outage merely because nodes = 0.

CASE B
Candidates = 10
M3-2 provider unavailable
Valid decisions = 0
Promotions = 0

→ BLOCK canonical persistence.

CASE C
Candidates = 10
Some valid decisions exist
Some candidates fail technical review
3 candidates safely PROMOTE

→ Do not trigger the batch-wide zero-node gate.
Normal existing behavior applies.

CASE D
Candidates = 0
No instructional candidate population discovered

→ Do not classify as M3-2 provider outage solely from zero nodes.
Existing mapping completeness/review rules apply.
