# PHASE 3 — SOURCE FIDELITY / COVERAGE GATE

## Forensic Audit — NO CODE CHANGES

Մենք անցնում ենք **Phase 3 — Source Fidelity / Coverage Gate** փուլին։

Այս փուլում **ոչ մի code փոփոխություն ՉԱՆԵՍ**։

Նպատակը նախ ամբողջությամբ հասկանալն է, թե ներկայիս Mapper-ը ինչպես է ապահովում.

**SOURCE → MAPPING**

և արդյոք հնարավոր է, որ textbook-ի իրական content block-ը կորչի, չծածկվի կամ mapping-ը սխալմամբ համարվի `completed`։

---

# 0. HARD RULES

Մինչև audit-ի ավարտը.

* ❌ ոչ մի code change
* ❌ ոչ մի prompt change
* ❌ ոչ մի DB schema change
* ❌ ոչ մի migration
* ❌ ոչ մի refactor
* ❌ ոչ մի behavior change
* ❌ մի փորձիր «շտկել» հայտնաբերված խնդիրները
* ❌ մի ստեղծիր նոր validation logic

Միայն.

**inspect → trace → test → report**

Եթե խնդիր գտնես՝ պարզապես գրանցիր այն։

Մենք code change-ի մասին որոշումը կկայացնենք audit-ից հետո։

# 2. IDENTIFY THE CANONICAL SOURCE BLOCK

Պետք է պարզենք.

**Ո՞ր object/field-ն է հանդիսանում canonical SOURCE BLOCK-ը։**

Գտիր դրա իրական interface/schema-ն։

Օրինակ՝ եթե կա նման բան.

```ts
{
  index,
  blockType,
  sourceText,
  sourcePage,
  sourceParagraph,
  ...
}
```

ցույց տուր իրական implementation-ը։

Պարզիր՝ source block-ի `index`-ը.

* unique է՞
* lesson-scoped է՞
* page-scoped է՞
* zero-based է՞
* one-based է՞
* երբևէ վերագրվո՞ւմ է
* sorting-ից հետո փոխվո՞ւմ է

Սա հատկապես կարևոր է coverage-ի correctness-ի համար։

# 3. TRACE SOURCE BLOCK → MICRO NODE

Գտիր այն exact code-ը, որը կապում է source block-ը MicroNode-ին։

Պարզիր.

```text
SOURCE BLOCK #N
        ↓
MicroNode.sourceBlockIndices
```

և պատասխանիր.

### A. Կարո՞ղ է մեկ source block լինել մի քանի MicroNode-ում։

Եթե այո՝ դա intentional է՞։

### B. Կարո՞ղ է source block-ը մնալ առանց MicroNode-ի։

Եթե այո՝ որտե՞ղ է այն պահվում։

### C. Կարո՞ղ է MicroNode ունենալ sourceBlockIndices = []։

Մենք արդեն ունենք safety net, բայց ստուգիր ամբողջ pipeline-ը։

### D. Կարո՞ղ է MicroNode-ը reference անել գոյություն չունեցող source block index։

Օրինակ.

```text
source blocks = [0,1,2,3]
microNode = [0,1,7]
```

Ինչ է տեղի ունենում։

# 4. COVERAGE VALIDATOR FORENSIC AUDIT

Գտիր `coverageValidation`-ի ամբողջ implementation-ը։

Չբավարարվես միայն function-ի անունը գտնելով։

Կարդա ամբողջ logic-ը։

Պետք է պարզես՝ ինչպես են հաշվարկվում.

* `totalBlocks`
* `coveredBlocks`
* `coveragePercent`
* `missingIndices`
* `duplicateIndices`
* `invalidIndices`
* `emptyMicroNodeTitles`
* `valid`
* category counts

Ցույց տուր validation formula-ն։

Օրինակ՝ արդյոք սա է.

```text
covered = union(all sourceBlockIndices)
missing = sourceBlocks - covered
```

թե ուրիշ մեխանիզմ է։

# 5. MOST IMPORTANT — WHAT COUNTS AS "COVERED"?

Սա audit-ի ամենակարևոր հարցն է։

Պարզիր՝ source block-ը համարվում է covered, եթե.

### Case A

այն կապված է MicroNode-ի հետ։

### Case B

այն կապված է Exercise-ի հետ։

### Case C

այն հայտնվել է Additional Exercise-ում։

### Case D

այն հայտնվել է Unmapped Blocks-ում։

### Case E

որևէ այլ պայման կա։

Գրիր exact logic-ը։

Հատկապես ստուգիր.

**Additional Exercises-ը coverage են համարվո՞ւմ, թե՞ ոչ։**

Եվ.

**unmappedBlocks-ը coverage են համարվո՞ւմ, թե՞ ոչ։**

Սա պետք է հստակ տարբերակվի.

```text
COVERED
PARTIALLY HANDLED
UNMAPPED
MISSING
```

Օգտագործիր արդեն առկա mappings-ը և գտիր իրական օրինակներ։

Յուրաքանչյուր lesson-ի համար ստացիր.


Հատուկ ուշադրություն դարձրու Lesson 103-ին, քանի որ նախկին audit-ում արձանագրվել էր.

Պարզիր.

* ինչ content էին
* ինչ blockType ունեին

* արդյոք mapping-ը nevertheless persisted/completed էր

**Մի փոխիր տվյալները։ Մի re-map արա։ Մի fix արա։**

# 10. DUPLICATE / INVALID INDEX FORENSICS

Ստուգիր.

### Duplicate

Եթե նույն source block-ը կապված է.

```text
MN1 → [1,2]
MN2 → [2,3]
```

արդյոք սա.

* valid shared coverage է՞
* duplicate է՞
* warning է՞
* invalid է՞

### Invalid

Եթե model-ը վերադարձնում է.

```text
[0,1,99]
```

իսկ source blocks-ը միայն.

```text
0..25
```

ինչ է տեղի ունենում։

Պարզիր.

* invalid index-ը strip արվո՞ւմ է
* mapping fail է՞
* warning է՞
* coverage valid մնո՞ւմ է

# 13. CURRENT CONTRACT VS REQUIRED CONTRACT

Համեմատիր ներկայիս behavior-ը մեր Phase 3 contract-ի հետ։

Պահանջը սա է.

### REQUIRED

1. Every real SOURCE BLOCK must be accounted for.
2. No source block may silently disappear.
3. Every MicroNode must have source evidence.
4. Every source reference must be valid.
5. Exercises/Questions/Activities/Tasks must be preserved.
6. Unmapped content must be explicitly reported.
7. Coverage failure must prevent a mapping from being considered fully completed.
8. Coverage must be measurable and auditable.
9. `SOURCE → MAPPING` traceability must be inspectable.
10. `MAPPING → SOURCE` references must be valid.

Յուրաքանչյուրի համար գրիր.

```text
PASS
PARTIAL
FAIL
```

և հիմնավորիր կոնկրետ code evidence-ով։
