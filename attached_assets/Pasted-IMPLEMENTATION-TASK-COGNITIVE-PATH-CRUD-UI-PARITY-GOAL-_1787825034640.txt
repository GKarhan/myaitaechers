IMPLEMENTATION TASK — COGNITIVE PATH CRUD/UI PARITY

GOAL

Make every Cognitive Path level fully editable and structurally identical
regardless of how it was created:

- AI-generated
- teacher-created manually
- teacher-edited after AI generation

This is a focused CRUD/UI consistency task.

Do NOT redesign Cognitive Path generation logic.
Do NOT change C2 planning semantics.
Do NOT change AI Teacher behavior.
Do NOT change quiz logic.
Do NOT change mapping semantics.

==================================================
0. INSPECT FIRST — NO CODE CHANGES YET
==================================================

Inspect the current Cognitive Path implementation and identify:

1. DB/schema/entity for cognitive levels
2. API create route
3. API update route
4. frontend create form
5. frontend edit form
6. fields currently stored for each level
7. which fields are present for AI-created levels
8. which fields are missing from manual-create UI
9. which fields cannot currently be edited after creation
10. how target-level / source flags are represented
11. how required evidence count is stored
12. how preferred interaction/question types are stored

Report the current field contract before editing.

Then implement the smallest systemic change.

==================================================
1. CANONICAL EDITABLE FIELD CONTRACT
==================================================

Every Cognitive Path level must support the same editable field set.

At minimum:

- cognitiveLevel / Bloom level
  - Հիշել
  - Հասկանալ
  - Կիրառել
  - Վերլուծել
  - Գնահատել
  - Ստեղծել

- performanceObjective
  - Կատարողական նպատակ

- successCriterion
  - Հաջողության չափանիշ

- requiredEvidenceCount
  - Պահանջվող ապացույցների քանակ

- preferredInteractionTypes / question types

Use the existing canonical interaction type vocabulary already present
in the system.

Examples already visible in current UI include:

- Բազմակի ընտրություն
- Ճիշտ / Սխալ
- Թվային պատասխան
- Կարճ պատասխան
- Ընդարձակ պատասխան

and any other existing supported types.

Do not invent a second interaction-type taxonomy.

==================================================
2. EXISTING LEVEL EDITING
==================================================

When teacher clicks Edit on ANY existing Cognitive Path level,
the edit form must allow editing:

1. Bloom/cognitive level
2. performance objective
3. success criterion
4. required evidence count
5. preferred interaction/question types

Currently Bloom level is not editable in existing levels.
Fix that.

Currently some manually created levels do not expose interaction types.
Fix that.

The edit form must be the same regardless of whether the level was:

- AI generated
- manually created
- previously teacher-confirmed

==================================================
3. MANUAL CREATE FORM
==================================================

The "Ավելացնել ճանաչողական մակարդակ" form must expose the complete
canonical contract.

Current behavior is incomplete because it mainly allows selecting the Bloom level
and text fields but does not expose the same question/interaction-type controls
available on AI-generated levels.

The manual create form must include:

- Bloom level selector
- performance objective
- success criterion
- required evidence count
- preferred interaction/question types

Use the same components, validation rules, and enums used by the edit form.

Avoid duplicate UI implementations if possible.

Prefer a shared CognitiveLevelForm component/schema.

==================================================
4. INTERACTION TYPE UI
==================================================

Preferred interaction/question types must be editable as a multi-select.

Teacher may select one or more supported types.

Example:

☑ Բազմակի ընտրություն
☑ Ճիշտ / Սխալ
☐ Թվային պատասխան
☑ Կարճ պատասխան
☐ Ընդարձակ պատասխան

Exact visual style should follow current teacher dashboard design.

Rules:

- preserve existing saved selections
- allow adding/removing selections
- do not silently erase types during unrelated edits
- if no interaction type is selected, preserve current validation behavior
  unless the existing backend requires at least one

Do not weaken backend validation.

==================================================
5. BLOOM LEVEL EDITING
==================================================

Existing levels must allow changing the cognitive/Bloom level.

Example:

Վերլուծել
→ teacher changes to
Հասկանալ

This must update the persisted level itself.

Do not create a duplicate level merely because Bloom changed.

After refresh, the edited Bloom level must remain persisted.

If cognitive level participates in ordering or target detection,
inspect and preserve those contracts.

Do not silently change target status unless the existing architecture
derives target status from level position/metadata.

==================================================
6. REQUIRED EVIDENCE COUNT
==================================================

Expose requiredEvidenceCount in both create and edit forms.

Teacher must be able to set a valid positive number within existing system bounds.

Example:

Պահանջվում է: 3

Teacher may change it to:

1
2
3
etc., according to current backend rules.

Use existing validation limits.

Do not introduce arbitrary new limits if a canonical validator already exists.

After save and refresh the value must remain persisted.

==================================================
7. AI-CREATED VS TEACHER-CREATED PARITY
==================================================

After this task, these two records must behave identically in CRUD:

AI-created Cognitive Level
Teacher-created Cognitive Level

The only difference may remain provenance/display metadata such as:

🤖 AI
✏️ Ուսուցչի կողմից հաստատված

But provenance must NOT control which fields are editable.

Teacher must have the same edit capabilities for both.
