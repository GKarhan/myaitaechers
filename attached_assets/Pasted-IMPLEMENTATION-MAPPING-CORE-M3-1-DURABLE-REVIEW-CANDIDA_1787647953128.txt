════════════════════════════════════════════════════
0. WHY THIS TASK EXISTS
════════════════════════════════════════════════════

The forensic audit of Lesson 717 / successful mapping job 185 established:

- provider raw Step 2 candidates: 22
- structurally accepted candidates: 18
- post-repair/normalization candidate/target records: 19
- source-first target records: 19
- promoted canonical MicroNodes: 1
- REVIEW_REQUIRED candidates: 16
- UNRESOLVED candidates: 2
- lesson-wide consolidations: 0

Therefore the mapper DID discover multiple independently meaningful,
source-backed candidate abilities.

The catastrophic reduction happened at the candidate-promotion boundary.

Current behavior is effectively:

candidate
→ promotion decision
→ PROMOTE => canonical MicroNode
→ anything else => candidate identity/pedagogical record disappears from
   the canonical path and source survives mainly as review-safe/unmapped material

This is safe for persistence, but it destroys too much diagnostic and
teacher-review information.

M3-1 fixes ONLY that information-loss problem.

M3-1 DOES NOT change which candidates are promoted.

2. CORE CONTRACT
════════════════════════════════════════════════════

that boundary in exactly one explicit durable state:

1. CANONICAL
2. REVIEW_REQUIRED
3. UNRESOLVED

IMPORTANT:

- learner delivery,
- Knowledge Tree canonical state,
- AI Teacher,
- quiz generation,
- Cognitive Path generation,
- Teaching Content generation.

This task preserves candidate identity for audit/review only.

8. FIX THE CANDIDATE-ID DIAGNOSTIC INVARIANT
════════════════════════════════════════════════════

The Lesson 717 audit found:

- 19 promotion decision records
- only 18 distinct candidate IDs
- t4:n0 appeared twice

Investigate this as part of M3-1 because durable review artifacts require
stable identity.

Do NOT patch Lesson 717 specifically.

Add a general invariant:

Within one mapping run, every candidate decision/artifact must have one
stable unique candidate identity.

Detect duplicate candidate IDs before durable diagnostic persistence.

Determine the actual cause of the duplicated diagnostic identity.

Fix only the general identity-generation/normalization problem if proven.

Do not silently drop one duplicate.

If two genuinely distinct candidates collide on the same ID:
- preserve both,
- assign deterministic unique identities according to the existing
  candidate identity architecture,
- record the collision diagnostic.

If the duplicate is merely the SAME candidate being appended twice:
- deduplicate the diagnostic record deterministically,
- preserve one authoritative record,
- record that duplicate emission occurred.

Do not merge pedagogically distinct candidates merely because IDs collide.
