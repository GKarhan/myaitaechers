==================================================
GOAL
==================================================

Remove artificial learner messages such as repeated:

"օկ"

when the backend already knows the next action and does not actually need
learner input.

Observed live runtime after Stage 3:

START
→ learner sends "օկ"
→ THEORY explanation
→ Stage = TASK_REQUIRED
→ learner must send another "օկ"
→ source exercise / generated task appears

Then after an answer:

learner ANSWER
→ evaluation
→ Decision Engine
→ FEEDBACK
→ cognitive level may advance
→ learner must send another "օկ"
→ next THEORY appears

This is technically safe but pedagogically and UX-wise unnecessary.

TARGET PRINCIPLE:

THE LEARNER SHOULD SEND A MESSAGE ONLY WHEN THE SYSTEM ACTUALLY NEEDS
LEARNER INPUT.

Server-owned transitions should continue automatically.

==================================================
1. DEFINE “LEARNER INPUT REQUIRED”
==================================================

Introduce or explicitly derive one pure rule answering:

DOES THE NEXT ACTION REQUIRE LEARNER INPUT?

Examples:

LEARNER INPUT REQUIRED:
- answer an active MICRO_CHECK
- answer an active source exercise
- answer a constructed-response task
- explicit learner-controlled HELP interaction
- genuinely explicit learner confirmation where product policy requires it

LEARNER INPUT NOT REQUIRED:
- THEORY completed and server already knows TASK_REQUIRED
- server has selected a source exercise and can deliver it
- server must generate/deliver a MICRO_CHECK
- cognitive level advanced and next THEORY must be delivered
- feedback was produced and server already knows the next non-interactive action

Do not use AI output to decide this.

This must be derived from authoritative server action/state.

server-owned transitions.

3. IMPORTANT — DO NOT COLLAPSE ARCHITECTURE
==================================================

Automatic continuation does NOT mean merging bounded AI jobs back together.

Maintain:

THEORY job
TASK job
EVALUATION job
FEEDBACK job

as separate bounded jobs.

The backend may sequence multiple server-owned actions in one HTTP request or
controlled continuation loop, but each bounded job remains independently:

- invoked
- validated
- persisted
- owned

Do NOT recreate:

one giant AI response
→ explanation + task + evaluation + feedback.

11. CONTINUATION LOOP
==================================================

Implement one controlled backend continuation mechanism rather than scattered
recursive calls or ad-hoc auto-send branches.

Use current repository conventions.

Conceptually:

while (
  phase2ActionIsServerOwned &&
  !nextActionRequiresLearnerInput &&
  continuationBudgetNotExceeded
) {
  execute next server action
  validate result
  persist state
  derive next action
}

Then return once:

- learner input required
- completion reached
- controlled failure occurs
- safety budget reached

Do not literally use a while loop if a different bounded approach is safer in
the current codebase.

The key is one explicit continuation owner.

==================================================

request.

THEORY

→ TASK_REQUIRED
→ ...

→ preserve consistent persisted state
→ log diagnostic

Do not use learner-facing blame language.
